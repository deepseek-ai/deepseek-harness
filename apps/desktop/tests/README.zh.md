# Desktop 本地验证

[English](README.md) | 中文

## 概述

本地下载和强更弹窗证据与生产后端联调、视觉验收、已安装应用升级分开记录。运行 [Desktop README](../README.zh.md) 中的命令可生成新的隔离报告。

已安装应用验收可显式启用 `DSH_DESKTOP_UPDATE_JOURNAL_DIR`，使用安装目录树之外、两个版本共同保留的绝对路径。每个主进程将已安装版本、状态转换和人工操作标记刷新到单独的 JSONL 文件。原始诊断和请求数据被排除；存储错误会向上传播。[日志决策](../../../.agents/notes/implemented/testing/2026-09-14-desktop-installed-update-journal.zh.md)定义证据的局限。单元与主入口测试覆盖日志记录；所选版本组合的结果通过[真实安装升级专项手测](#verification-installed)确认。

## 故障报告验证

产品行为与限制见[故障恢复与诊断](../docs/diagnostics/README.zh.md)。

使用可丢弃的 profile、独立的 Electron `userData` 和实际打包客户端。构造最小本地组合包：`package.json` 的 `dsh.bundle.patch` 指向 `cordis.patch.yml`，需要执行代码时再加入插件模块，然后打成可本地安装的 `.tgz`。这些包会故意使应用出错，不得发布或安装到日常 profile。

分别构造模块导入异常、插件初始化异常、`appReady` 后的异步异常，以及 Host 非零退出。用 patch 禁用 `agent`、`session`、`llm`、`tools` 提供者，检查服务缺失诊断。跨重启场景通过 `pluginManager` 选入该组合包，再重启同一 profile。运行期场景须实际观察客户端就绪；`appReady` 不代表窗口已经显示。

检查原始错误与 cause 或退出码、跨重启的操作 ID 和 Host 运行 ID、报告收集完成标记与遗漏信息、原生弹窗中的文件获取，以及禁用插件恢复后的启动。记录安装包版本和源码提交；生成测试包成功或管理操作返回成功，都不能代替客户端功能验证。测试后恢复协议关联并退出测试进程。

资源验证可构造大型稀疏历史文件、大量无关文件、密集记录，以及损坏行和未完成行。在独立新进程中测量，分开记录数据构造与收集开销，并核对实际读取量、输出大小、耗时和峰值内存。验证 Worker 取消时，可用仅测试加载的模块钩子在写入进入标记后挂起异步文件打开操作；先确认标记，再观察期限到达后的 Worker 退出，并逐字节核对基本报告。该方法不模拟内核系统调用卡死，也不代替打包客户端验证。

## 更新弹窗主题

执行 `pnpm --dir apps/desktop run build` 后，在 macOS 上运行真实 Electron 配色夹具：

```sh
apps/desktop/.desktop-build/targets/mac-arm64/electron/Electron.app/Contents/MacOS/Electron apps/desktop/tests/fixtures/update-theme.mjs
```

夹具创建独立 profile，加载生产壳 HTML、sandboxed preload、渲染脚本及打包的 design token，仅替换固定 IPC 状态响应。12 个用例覆盖普通和强更文档的浅色／暗色初始状态、打开时切换及跟随系统。它检查文档背景透明、卡片／文字／按钮／遮罩配色、代码／地址表面、仅暗色显示的 1 CSS px 内描边及普通弹窗关闭图标，并将四张截图和 `result.json` 写入 `.desktop-build/qualification/update-theme-*`。它不启动 Host、不下载更新、不运行安装器，也不验证 Windows 原生渲染。首次关闭提示共用普通文档的 CSS 和主题脚本。

## 原生浮层可见性

在 macOS 上，编译 Desktop Host 源码后复用缓存的 Electron 运行时：

```sh
pnpm exec tsc -b apps/desktop/tsconfig.host.json
apps/desktop/.desktop-build/targets/mac-arm64/electron/Electron.app/Contents/MacOS/Electron apps/desktop/tests/fixtures/update-overlay-visibility.mjs
```

夹具使用独立 profile，在 `.desktop-build/qualification/update-overlay-*` 下写入 `result.json`。它检查可见和隐藏的父窗口、不创建原生子窗口、父窗口可见性通知后独立对照窗口仍保留焦点，以及销毁父窗口时的视图和输入清理。它不使用网络、产品登录或 dsh Host。这项验证覆盖窗内承载方式，不覆盖完整的首次登录或安装流程。

## 手动演练

Host、客户端与 Desktop 产物构建完成后，在 Windows 仓库根目录运行 `node --import tsx apps/desktop/scripts/test-workspace-updates.ts --interactive`。真实工作区持续打开，并提供独立控制窗口。其菜单可选择普通或强制更新、保持和放行下载、注入下载失败，以及添加或清空测试任务。失败模式须在开始下载前选择。确认安装并完成任务收尾后，fixture 消息提示安装器调用已被拦截；确认消息结束演练。关闭控制窗口也会退出。每次运行独占私有 profile 和回环服务器；载荷不是安装器。重新运行命令开始新一轮。省略 `--interactive` 则运行自动化场景，保留 120 秒截止时间和自动退出；交互模式下载的网络截止时间为十分钟。

## 真实安装升级专项手测

当改动可能影响更新选择、下载、安装、重启或数据保留时，使用本指南。操作者根据受影响的平台和改动选择场景，无需每次提交或发布都跑完整矩阵。agent（智能体）可以为本轮取包、准备临时脚本和本地服务器，并收集证据；这些辅助工具不必纳入仓库维护。最终验收结论由操作者负责。

### 准备本轮验证

1. 记录平台、架构、源码版本、起始版本、目标版本和预期行为。安装测试使用允许升级的版本组合；相同或更低版本用于拒绝更新的测试。已有构建和产物获取方式见[打包指南](../packaging/README.zh.md)。
2. 确认本轮影响的安装和数据范围。优先使用专用系统账户或虚拟机，或具有独立身份和数据路径的测试应用；只复制应用目录不能隔离安装注册信息或用户数据。记录实际应用、用户数据、Harness home 和更新缓存路径；两个版本必须使用同一份测试数据。测试分发 URL 本身也不提供这种隔离。替换前保留已有安装和数据。
3. 改变更新源之前，先启动起始版本并确认工作区可用。创建可辨认的测试会话和设置，供升级后核对。保存原更新配置，记录清理缓存等仅为测试进行的改动。

### 将应用指向本地更新源

准备仅监听 `127.0.0.1` 的服务器，提供目标包及匹配的更新清单。Windows 更新使用已签名 NSIS EXE，macOS 更新使用应用 ZIP；DMG 可用于安装起始版本，不能代替更新 ZIP。按实际文件字节核对清单中的版本、文件大小和 SHA-512，保持下载所得的安装包不变。清单文件名应匹配被测版本实际请求的渠道，不照搬旧实验的文件名。确认请求确实到达该服务器。按所选场景需要添加请求日志、传输限速、故障或 HTTP Range 支持；普通静态服务器不能证明差分下载行为。

重定向之前，检查被测版本如何确定更新源。已打包应用读取 `app-update.yml`，当前 provider 在首次检查后缓存配置；修改文件不保证运行中的进程采用新地址。根据该版本的加载行为协调修改和重启时机，并核对实际请求 URL。临时 macOS 实验中，修改 `Contents/Resources/app-update.yml` 会改变已签名资源：保留原文件，记录签名影响，不将修改后的起始应用视为未经改动的发行包。另行准备的测试应用可以在签名前写入更新源配置。保持发布者校验开启，两个平台分别使用各自已安装应用验证。

起始应用准备好之前，服务器提供起始版本，之后再切换到目标版本。渠道或迁移改动应为各场景准备相应设置，按照[当前渠道规则](../README.zh.md#updates)确定预期渠道。验证解锁和切换动作时，通过真实 UI 操作。包内渠道标记不能单独决定运行时渠道；没有发现更新时，先检查版本顺序和灰度命中条件，再判断是否为更新源故障。本地响应验证客户端行为；已部署的路由和公网 CDN 分发需要针对对应服务另行检查。

### 验证受影响的行为

| 改动涉及的行为 | 按需选择的手测内容 |
|---|---|
| 渠道选择或设置迁移 | 既有设置、全新 profile、解锁、显式切换及重启后的持久化；检查实际清单请求和候选版本 |
| 下载或校验 | 中断或挂起真实传输，恢复服务后显式重试；按改动需要检查哈希或发布者不匹配时的拒绝行为 |
| 差分下载 | 提供所需旧包／缓存和 blockmap，支持 Range 请求，并通过请求日志区分差分重建与全量回退 |
| 安装、任务收尾或重启 | 从真实应用确认安装，观察旧进程退出和新进程启动，检查与改动相关的失败或恢复界面 |
| 数据路径或持久化 | 在新工作区核对准备的会话和设置，包括预期的渠道迁移或显式选择保留 |

改动影响安装或重启时，包含一次成功的真实安装。不能用安装调用记录或界面版本标签变化代替。核对新进程、已安装包版本、文件替换和工作区可用性，并按测试包采用的签名方式检查签名。共享 runtime 或其他精简包不能证明完整包资源替换或独立启动。

### 记录结果并恢复环境

保存包标识和哈希、起止版本、所选场景、请求／应用日志、相关截图、仅为测试进行的改动，以及通过／失败／未执行的结论。记录日志无法证明的用户观察。上文所述可选 journal 用于补充这些检查；完整事件序列本身不代表数据保留或视觉验收通过。

只停止本轮拥有的服务器和进程。按实际情况恢复临时设置，并核对最终更新地址。仅在旧 `app-update.yml` 备份仍属于当前安装版本时恢复它，绝不将旧包配置覆盖到升级后新版本的配置上。保留用户要求的安装包和证据。本地手测不修改生产更新源。

## 验证证据

构建 Desktop 后，`node apps/desktop/scripts/test-update-channels.mjs` 使用本地回环清单和下载的无执行能力文件检查固定版本的 Electron updater。它验证渠道文件名、禁止降级、灰度命中，以及切换渠道后实际下载缓存和过期确认的撤销，在 macOS 上还关闭 updater 创建的本地交接服务。Windows pull request CI 将依赖版本与已提交的验证记录比对；此真实 Electron 检查需单独运行。不运行安装器、Host 或远程发布。此验证不能替代 Windows 和 macOS 的签名安装应用测试。

本地命令构建 Desktop，并在 Electron 44 中运行真实 HTTP updater、策略客户端、沙箱预加载和强更页面。它记录每个场景，并把报告保存在 `.desktop-build/qualification/local-updater-*`。安装器调用、外部浏览器和剪贴板均替换为观测记录；下载字节不是可执行安装器。

[构建后 Host 场景](fixtures/host-update-qualification.mjs) 使用真实 profile Loader、standard agent 预设、任务服务和 Node 后台进程。它验证排队的轮次／步骤、运行中的模型请求、等待答复的提问／审批、运行／停止中的全局和 agent job、不会取消任务的准入锁定、准入恢复，以及 Host 释放后的检查拒绝。仅模型响应和人工答复使用替身。两个独立调用使用私有 profile 和会话数据并发通过；全部自有 agent、job 和 Host 完成后才写入成功报告。

[Electron 工作区运行器](../scripts/test-workspace-updates.ts) 在私有目录中执行编译后的主入口，使用真实预加载、工作区和独立 Host 进程。它确认首次启动声明，并通过 Electron 输入事件及嵌入式 Windows frame 的 Chromium 调试器输入操作页面按钮。私有应用复用已准备的目标运行时资源。已有 Windows 运行记录中十个场景通过，覆盖菜单反馈、下载失败与重试、独立安装确认、确认期间真实任务创建、推迟安装、强更阻塞和真实 Host 停止超时。普通与强更失败均恢复替代 Host，并要求重新确认安装；恢复不会清除强更策略。分发使用本地服务器，安装被拦截；这些不是签名已安装应用的验证结果。macOS 工作区路径尚未完成验证；这些 Windows 结果不覆盖它。

[Windows 验签运行器](../scripts/test-windows-update-signature.mjs) 使用已安装的 electron-builder 元数据生成器和 `NsisUpdater` 验签器，输入为公开发布证书和真实可执行文件。发布者属性匹配时通过；同一有效签名在预期发布者不同时被拒绝，未签名可执行文件也被拒绝。缺少发布者的负对照确认验签被跳过。单元回归覆盖 DN 转义、不完整身份，以及显式或宿主默认 Windows 目标；移除发布者配置会使两条元数据用例失败。此检查不下载、安装或签名产物。

[签名下载运行器](../scripts/test-signed-updates.mjs) 连接真实 Electron HTTP、`NsisUpdater`、Windows Authenticode 和构建后的协调器。四个场景通过：哈希正确但发布者错误时拒绝、哈希正确但未签名时拒绝、传输损坏先于验签被拒绝，以及显式重试后签名文件就绪并单独交接安装。被拒绝的可执行文件缓存为空，自动检查不发送重试请求，已准备的下载保持可用，原始输入的 SHA-512 不变。合成清单和测试应用适配器不证明已安装版本兼容性；不会启动安装器或 Host。

提供旧安装器和两个原始 blockmap 后，同一运行器还会验证单段 Range、多段 Range 重建、缺少旧 blockmap 时回退，以及 Range 被拒绝时回退。重建的可执行文件通过 SHA-512 和 Authenticode 检查。请求记录区分差分负载字节与全量下载；全量回退不能满足差分成功断言。这些回环结果不证明 CDN Range 支持或已安装应用的缓存可用。

## 待验证事项

以下事项不是通过证据，review 时必须保持可见：

- Electron `capturePage()` 捕获单个窗口。Windows 交互观测包含合成弹窗和原生菜单选择，但跨平台 Figma／布局验收与完整录制仍未验证。自动化工作区运行器直接调用菜单处理器。
- 开发启动器在此 Windows 工作区遇到指向缺失目标的可选 Linux ARM64 依赖 junction；验收运行器直接链接已有依赖图，不验证该启动器的依赖投影。
- fixture（测试前置数据）不执行安装器，不覆盖已安装应用，也不证明新版本成功启动。发布前仍需签名 Windows 和 macOS 的已安装版本验收。
- 包检查和 fixture 结果不代表另一组已安装版本的升级结果。通过所选手测记录启动、失败重试、重启和数据保留情况。
- 真实策略源站、网关行为、限流、批准的页面源站和已部署策略配置仍待后端联调。本地响应不能证明线上服务可用。
- 策略、updater 清单与下载停滞均达到真实截止时间并可恢复。下载写入的 `ENOSPC` 故障注入已覆盖；真实卷耗尽与已安装版本升级的磁盘压力仍未验证。差分下载和发布者拒绝已通过真实 Electron 下载验证，但尚未在新打包应用的已安装版本升级路径中验证。
- Windows 原生剪贴板写入通过。已尝试启动默认浏览器，但因自动化工具无法可靠识别当前 URL，目标地址验证停止。macOS 浏览器和剪贴板集成仍未验证。
- 强更与常规失败使用本地化摘要和折叠诊断；复制失败展示可选择的地址。常规错误悬停提示显示摘要，不展示原始诊断。Windows／macOS 安装包的图标提醒、通知权限与专注模式行为仍未验证。
- 完整 `doc-sync`（文档同步门禁）在文档站测试中遇到 Windows 文件符号链接 `EPERM`。这不是 updater 失败，也不代表完整文档门禁通过。
