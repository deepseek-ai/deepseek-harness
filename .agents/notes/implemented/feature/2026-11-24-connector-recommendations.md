# Agent Note: Recommendation cards install official connectors

Status: implemented

English | [中文](2026-11-24-connector-recommendations.zh.md)

## Problem

The official connectors to Feishu, WeCom, DingTalk, Tencent Meeting, Notion, Tencent Docs, and Linear are separately installed packages. Before installation the Plugins page's own lists show nothing about them, and the recommendation card could offer only the optional bundles the installation ships. When a user's task needed one of these apps, or the user asked whether DSH can reach one, the conversation offered no way to the connector: the model could not name it, and the card could not install it.

## Decision

The `official-plugins` skill and the `enable_official_plugin` card kind of [plugin recommendations](../../../../packages/extensions/plugin-recommendations/README.md) also cover the connectors. [`dsh-official-bundles`](../../../../packages/util/official-bundles/README.md) lists them as `CONNECTOR_BUNDLES`, apart from `ON_DEMAND_BUNDLES`, and the generator of the on-demand catalog also embeds `OFFICIAL_CONNECTOR_CATALOG`: each connector's title and description in every shipped language from its own `locale/*.json`, and its icon, kept current by `verify-official-bundle-catalog`. The plugin manager reads neither, the Host package reads the catalog, and a test fails while a connector package is missing from it; the English title is the app's name, which the skill's catalog entry also uses. The catalog the skill loads appends one English entry per connector with `installed` and `enabled` read from the same plugin manager listing and classified as the card classifies the connector, so an installed connector the card cannot enable is left out, and the skill tells the model to offer a connector when the user's own request needs its app and the connector is not enabled, or is enabled but its account is not connected, where the card's Connect account opens the connector's page, ordinary tasks included, but to offer none when one of its tools already belongs to that app, such as its MCP server, and to use that tool instead. The skill's one-line entry in the session's skill catalog, the only text the model sees before loading the skill, depends on the profile: it is composed from the plugin manager's listing and names only the apps whose connector a card could offer now, because the profile does not hold it or holds it usable and switched off. Every lookup, from any working directory, reuses the composed entry until Plugin Manager's `plugin-manager/changed` event discards it and invalidates the cached catalogs, so the listing is read once per start and per Plugin Manager change.

A click on the card of a connector the profile does not hold installs it in the background through `pluginManager.installBundle` with `<name>@<DSH runtime version>`, an exact saved version, and the same package and version as `expected`; the installation enables it. When pnpm stops the installation on install scripts, the decision records the names awaiting approval; any other failure records none, because the plugin manager lists every undecided script in the profile after any failed run. The card lists the recorded names, and the separate `approve` verb installs again with `approvedBuilds` set to exactly those names, never names the browser sends; when the connector is installed by then, `approve` enables it as `enable` does. Enable, install and approve on a connector card first switch on the Connectors tab bundle when it is off; a failure there is logged and the action continues. Once the connector is enabled, the card shows Connect account beside its status, unless the user dismissed the card or its last attempt failed; the button opens the connector's page in Plugins through the existing `pluginNavigation.openBundle`. A connector the profile does not hold has no plugin manager listing or details page, so its card shows the connector catalog's title and description in the interface language as plain text.

The change stays inside the two recommendation packages and `dsh-official-bundles` with its catalog generator: the plugin manager, the Plugins page, the action card service and frame, the connector packages, and the Connectors tab, which keeps its own connector list, are unchanged.

## Alternatives considered

**Opening the Plugins page install dialog from the card.** The dialog already shows progress, handles blocked install scripts, and offers Enable now. Reaching it needs a new cross-plugin entry into the Plugins page, because `pluginNavigation` opens only a bundle's page or the list, and it moves the user away from the conversation that needed the app before anything is installed.

**Registering the connectors in the on-demand official catalog.** The plugin manager already lists, installs, and enables the entries of `ON_DEMAND_BUNDLES`. Uninstalled connectors would then appear in the Plugins page's own lists, which the [Connectors tab note](2026-11-01-connectors-tab.md) avoids by keeping them out of `ON_DEMAND_BUNDLES`; the separate `CONNECTOR_BUNDLES` gets the same generated metadata without entering those lists.

**Recommending only the Connectors tab bundle.** The bundle is already a shipped optional plugin in the catalog, but its description names no app, so the model cannot match a task to a connector, and the user still installs the connector by hand from the tab.

**A separate skill for connectors.** A second skill adds a second line to every conversation's skill catalog, and two skills would compete for the one card a Turn shows.

**A fixed entry naming all seven apps.** The entry would not depend on the profile, but a user whose connector is already enabled would load the skill on every task that names that app, only to learn that nothing is to be offered.

## Consequences

The user installs and enables a connector without leaving the conversation, and the model can offer one during an ordinary task. Installing works whenever the connector package is published to npm at the running DSH version, so a build whose version is not published cannot install a connector from the card. The connector catalog carries each connector's own text in every shipped language, so the card of an uninstalled connector shows it in the interface language. The catalog is compiled into the installation, so a new connector reaches the card only in a new DSH release, and adding one updates both `CONNECTOR_BUNDLES` and the Connectors tab's own list. The account is connected on the connector's page in Plugins, which the card opens without tracking the connection. Allowing install scripts runs third-party code with the user's permissions, so the card lists the packages, the approval is a separate click, and the Host allows only the names the failed installation recorded. The skill catalog entry and the loaded catalog grow by the amounts the package README's Model Experience section states. When a connector is enabled, the model receives one replacement skill catalog whose entry no longer names that app, and later tasks that need the app no longer load the skill; a profile change made outside Plugin Manager reaches the entry only at the next Plugin Manager change or restart.
