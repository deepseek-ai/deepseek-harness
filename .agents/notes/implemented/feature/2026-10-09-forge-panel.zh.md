# Agent Note: 变更请求面板与 worktree Session

Status: implemented

[English](2026-10-09-forge-panel.md) | 中文

## Problem

[Session 变更请求绑定](2026-10-09-session-change-request-bindings.zh.md)为每个 Session 提供了变更请求列表，但没有地方展示。让 agent 开变更请求的用户需要在不离开对话的情况下看到它们的检查、评审与能否合并，也希望新 Session 的修改和提交不影响当前检出。Git 必须在 Session 命令运行的地方执行，这可能是远程或受限的执行环境；检查不能改动仓库，而且 worktree 必须在模型第一次动作之前就存在。

## Decision

[`dsh-experimental-client-ui-forge`](../../../../packages/experimental/client-ui-forge/README.zh.md) 是一个双端包。宿主端的 `forgePanel` Remote 把面板为一个 Session 展示的全部内容组装成一条流式状态；forge 注册表与绑定服务只保留各自的领域操作。客户端包括[会话面板](2026-11-05-session-panel.zh.md)中的“变更请求”分栏、检出行与本地变更行和提醒标记，以及一个变更视图、一个新会话选项、一张位于输入框上方的创建卡片、一个 toast，以及[会话列表中的图标与悬浮卡片部分](2026-10-20-forge-session-list.zh.md)。所有界面都把已绑定的条目称为变更请求（forge 注册表的术语），不随代码托管平台的叫法变化。[forge 套件](../../../../packages/experimental/forge-bundle/README.zh.md)把面板、forge 注册表、GitHub 提供方、绑定服务、工作树模型工具与面板使用的一个隔离 worktree 服务作为插件页中默认禁用的一个条目发布。

评审与工作树控件服务于同一个代码修改流程。统一插件入口让用户可以一次启用这些能力，无需根据底层包的拆分判断应该开启哪张卡片。包与两套工作树服务仍保持独立，分别负责会话开始前和对话中创建工作树的流程。

Remote 通过 Session 的子进程提供方，按其[解析出的权限与查询限制](../bug-fix/2026-10-28-forge-git-session-permissions.zh.md)检查检出，因此它读到的与 Session 命令看到的相同。检查读取顶层目录、Git 目录与公共 Git 目录、分支或缩写的 HEAD 提交、上游与远端，以及分支相对于其分叉点的变更规模。它在 Session 被关注时、每个 `workspace-root/change`、`tool/result` 与 `sandbox/mode` 事件之后以及刷新时运行，一次只运行一个，最多再追加一次。

状态轮询跟随面板订阅：只有该 Session 的某个界面挂载时才监听其绑定，注册表停止轮询无人监听的变更请求。每张卡片保留最近一次轮询得到的快照，因此短暂的失败不会让标题与编号消失。Session 只有一个打开的变更请求时，它的卡片默认展开；有多个时全部折叠；用户第一次展开或收起卡片后，以用户的选择为准。

展开的卡片可以把草稿标记为可评审，也可以合并主机现在就会合并的变更请求。forge seam 把两者作为提供方操作承载，失败时返回带类型的结果；每个快照都说明主机现在是否会为已登录用户合并该变更请求、仓库允许哪些合并方式，因此面板只提供能够成功的操作。合并带上卡片显示的 head 提交，有新提交到达后主机会拒绝。面板只操作绑定到该 Session 的变更请求。

新 Session 通过请求而不是立即创建来以 worktree 开始。勾选新会话那一行中的选项（一个 `conversation.hero.options` 条目）会追加一条带基准分支的 `plugin:client-ui-forge/worktree` 记录；更换基准或取消勾选会再追加一条；用户发送之前不会改动仓库。只有创建能够成功时才提供该选项：在 `workspace-write` 下，检出及其公共 Git 目录必须位于可写根之内，这排除了本身就是链接 worktree 的项目。worktree 必须在第一条消息的这一轮开始之前就存在，这样这一轮才会在其中运行，第一次请求也已经写明新目录。消息进入 Session 的收件箱时，面板的 `agent/inbox/inserted` 监听器在这次投递唤醒 Agent 之前启动 Agent 的维护任务；Agent 会暂存唤醒直到维护任务结束，面板在维护任务内创建并进入 worktree。创建的阶段以流的形式推送给输入框上方的卡片，卡片上的“取消”停止这次尝试。尝试被停止或失败后，消息继续在收件箱中等待，卡片保留失败信息，并提供用新分支名再试一次，或“不使用工作树”：撤回请求并让消息继续。一个 `agent/pre-step` 监听器仍会在请求未完成的 Session 的第一个步骤提议中创建 worktree，因为 Agent 正在运行一轮或其他维护任务时进入的消息不会被暂留；它把工作目录通知移入本步提议的消息，失败时这一轮结束。`forgeWorktree` 投影忽略第一个 `turn/start` 之后的请求以及第一个 `step/start` 之后的创建，因此运行中的 Session 永远不会移动。标签页顶部一行写出 Session 所在的分支，会话列表标出在所创建 worktree 中工作的 Session。

Session 所在的 worktree 可能在 Session 之外被删除。每次检查都会确认所创建 worktree 的目录是否还在；Agent 空闲时进入的每条消息都会启动一次暂留并再确认一次，目录缺失期间消息等待、不开始这一轮。这次确认必须发生在这一轮之前：组装一个步骤的上下文时，工作目录服务会把目录已不存在的 Session 移回其项目，而这发生在任何 pre-step 监听器运行之前。“恢复”在记录的目录重新检出分支；分支也已删除时，在其基准提交重新创建分支。“在项目目录继续”把 Session 移回源检出。两者都在暂留内运行，之后放行等待中的消息。

面板不在现有 worktree 之间移动 Session。移除变更请求会追加一条 `dismiss` 记录，它的 toast 通过 `track` 提供“撤销”。

面板还通过变更视图展示 Session 工作背后的变更；变更视图是本包的一个资源标签页类型。Remote 在宿主上把每个 diff 解析成文件与 hunk，因此浏览器无需补丁解析器即可绘制，每次读取都受 `maxDiffBytes` 与 `maxUntrackedFiles` 约束。本地变更来自使用 Session 权限与执行环境的 `git diff`，范围由用户选择：默认是分支相对于分叉点的变更，也可以是未提交、未暂存或已暂存的变更；未跟踪文件经 Session 的文件系统读取，显示为新文件。变更请求的变更来自代码托管平台，取自绑定最新状态中的 head，经 forge seam 新增的两个提供方读取操作 `diff` 与 `fileText` 获得。Host 为每个变更请求保留最近读到的补丁，按 head 提交与目标分支区分，总量受 `maxCachedDiffBytes` 约束，因此在同一 head 下重新打开、刷新与导航都不会再次下载；托管平台或提供方因结果超过其大小上限而拒绝时报告 forge 失败 `too-large`，视图随之提供变更请求的网页而不是重试。hunk 之间未变更的行从文件的新版本展开，即工作树、暂存区或 head 提交，并且只在该文本仍与 hunk 吻合时展开。每次检查还会为变更卡片统计分支的变更规模；没有打开中的变更请求以当前检出分支为源分支时才显示该卡片。卡片上的“创建变更请求”向 Session 发送一条用户消息，由 Agent 用自己的工具创建变更请求，绑定像其他变更请求一样来自 `gh pr create`。

变更视图也写 checkout，粒度是整个文件：“未暂存”范围可以暂存和还原，“已暂存”范围可以取消暂存。评审 Agent 工作的人把认可的部分放进暂存区、丢弃其余部分，没有这些写操作就得离开应用去做。读者按下按钮就是授权，正如归档之于 worktree 服务移除 checkout，所以写入命令不受 Session 沙箱策略约束：该策略约束的是 Agent 的行为，读者可以在只读的 Session 里暂存，也可以在目录位于 checkout 根目录之下的 Session 里暂存。暂存和还原为每个文件带上读者所见改动的 digest，Remote 重新读取 `unstaged` 范围，改动不同就拒绝写入：从读者看到文件到按下按钮之间，Agent 可能又改了它。暂存和取消暂存的撤销，是把暂存区条目恢复到写入之前写出的 tree。还原没有撤销，所以先询问。

本地变更视图读取的不只是 Session 自己的检出。标题栏开头的菜单可以选择仓库的另一个本地分支或远程跟踪分支。仓库里有 worktree 检出的分支在该 worktree 里读取，四个范围都可用，这样就能看到子智能体在自己的 worktree 里改了什么，包括未提交的文件；没有 worktree 检出的分支只显示已提交的内容。本地范围用可选的 `head` 表示这个选择，而不是给视图增加第二种来源，所以每次读取、透镜请求、已审阅标记的键和已加载数据的键都通过它们本来就接受的范围带上它；Session 自己的检出不带 `head`，所以浏览器为它保存的已审阅标记和评论记录保持原有标识。页面只发送分支引用，从不发送路径：Host 校验引用，向 Git 询问哪个 worktree 检出了该分支，通过检查确认那里是同一个仓库的检出并且确实检出了它，再以读取方 Session 的沙箱策略在那里运行 Git。没有选择基准时，其他分支与 Session 自己的 HEAD 比较，而不是像 Session 自己的检出那样与远端默认分支比较：查看子智能体分支的人想知道的是它离开 Session 的工作之后改了什么；这种比较在没有远端的仓库里也成立，并且不会把 Session 派出任务之前自己的提交算进去。其他 `head` 是只读的，插件插槽和行注解只留给 Session 自己的检出，所以其他插件使用的 `ctx.forgeChanges` 不变。Session 面板的本地变更行在每个 Git 检出内都显示，没有变更时显示空的行数，这样当 Session 自己的检出没有变更、而它的子智能体在 worktree 里工作时，也能打开视图和菜单。

评审评论在用户选择代码时固定文件、侧、行范围、完整 hunk 与所评审的 head。Agent 引用进入既有输入框引用机制，由用户决定批量发送，发送后的消息记录模型实际收到的内容。GitHub 写入属于 forge 提供方的可选操作：预检核对当前 head，写入明确指向该提交；结果不明时阻止再次写入，直到用户核对。Agent 引用与已发布评论的行内记录以及评审总结归浏览器页签实例所有，不进入 Session 日志；留待之后一起提交的 PR 评论写入代码托管平台的待提交评审，见[待提交评审决策](2026-11-05-forge-pending-review-drafts.zh.md)。切换 Session 保留该实例；关闭时丢弃本地状态并拒绝迟到的写入结果。已发布的 GitHub 评论仍保留在外部平台。

## Deferred

本节曾暂缓的左侧导航代码审查页已实现为[代码评审页](2026-11-11-forge-review-page.zh.md)；它的列表来自可选的提供方能力，页面按 URL 读取变更请求，因此本包的会话界面没有改变。

变更视图目前还没有单个提交与上一轮的范围；两者将是经 `localDiff` 读取的更多 `ForgeLocalScope` 种类。

## Alternatives considered

**按平台使用不同名称。** 在 GitHub 上称 pull request、在 GitLab 上称 merge request，需要每个提供方声明自己的名称，所有文案也要随之变化；而 GitHub 是唯一的提供方，统一的术语让文案保持不变。

**通过 `gh pr merge` 合并。** 必需检查尚未完成时它会启用自动合并，基准分支要求合并队列时它会加入队列，因此一次点击可能安排了一次以后的合并而不是立即合并。REST 合并接口要么立即合并，要么拒绝。

**合并后删除 head 分支。** Session 的 worktree 可能就在这个分支上。

**为 Git 检查单独建一个宿主服务包。** 目前没有第二个使用方需要检出信息；出现模型工具时，可以再把它们移入共享服务。

**以宿主进程运行 Git。** 远程与受限的执行环境会显示宿主的文件而不是 Session 的文件，宿主还会读取 Session 无法读取的目录。

**勾选时立即创建 worktree。** 每次切换勾选或更换基准都会创建并丢弃一个检出，而且用户决定发送之前 Session 就已经移动。

**在创建 Session 的请求中携带该选项。** 这个请求由 Session 控制器拥有，字段是封闭的；插件记录让选项留在本包之内，并且在空白 Session 重新加载后仍然保留。

**在面板中切换现有 worktree。** 切换后的 Session 仍保留其项目的沙箱根，因此项目之外的 worktree 依然只读；对话中途移动还会让模型对文件的认识前后割裂。让 Session 从一开始就在自己的 worktree 中运行可以同时避免这两点。

**把选项放在输入框工具栏。** 发出第一条消息后工具栏依然存在，而那时该选项已不再适用；新会话那一行在 Session 开始后就会消失。那一行原先只提供单值 slot，因此 `ui-conversation` 增加了列表型 slot `conversation.hero.options`。

**在第一轮之内创建 worktree。** 第一个步骤提议运行时这一轮已经开始：上下文按旧目录组装，失败只能结束这一轮并丢弃已认领的消息，而工作目录服务已经把 Session 移出被删除的 worktree。它只作为没有被暂留的消息的兜底。

**在 Agent 接纳阶段暂留消息。** `agent-controller/admission` 阶段会在消息进入收件箱之前暂留它，因此 worktree 建好之前消息一直留在输入框里，失败时退回以便编辑。它需要在每个发送方的投递之前加一个控制器服务，单个面板不足以支撑这项核心改动；在收件箱插入时暂留只用现有的收件箱事件与维护任务，并覆盖所有发送方。

**把等待中的消息退回输入框。** 宿主接收消息之后，输入框没有办法把它收回，除非为一个插件在会话包里新增公共 API；消息改为在卡片的操作下继续等待。

**在 Web 输入框里设发送闸门。** 浏览器在宿主看到消息之前就拦住它，因此每次检查都要一次 Remote 调用，被拒绝消息的阶段只存在于浏览器中，其他发送方也会绕过它。在收件箱插入时暂留，让消息停在它进入 Agent 的位置，并把失败保留在面板状态中。

**把创建卡片放进对话记录。** 对话记录的节点不接受插件定义的类型；输入框上方的停靠区是最近的列表型 slot，而且它在新会话页也会渲染。

**手动粘贴 URL 跟踪。** 它与 Session 自己的命令记录下的绑定重复。绑定来自 `gh pr create`、操作单个变更请求的 `gh pr` 命令、推送以及检出所跟踪的分支，`track` 保留给“撤销”使用。

**在浏览器中解析补丁。** Remote 将传输不受限的补丁文本，浏览器也需要补丁解析器；宿主约束读取并只解析一次。

**复用代码审查标签页的文件对比。** 它属于另一个插件，本包在运行时不能导入；把它移入共享基础组件又会为一个使用方改动共享包。变更视图改用共享的高亮器、菜单、提示与 diff 颜色 token 构建。

**从本地仓库读取变更请求的 diff。** 当前检出分支可能领先或落后于托管平台，基准分支也可能没有拉取；评审者看到的是托管平台的 diff。视图改为在当前检出分支有超出 head 的提交时给出说明。

**在面板里根据失败信息识别 diff 过大。** 失败信息属于提供方及其托管平台，会随它们变化；失败代码让每个提供方报告自己的上限，面板只按代码分支。

**直接在卡片上创建变更请求。** 面板需要推送分支并撰写标题与描述；发送消息让 Agent 用自己的工具和用户的指示完成这两件事，绑定变更请求的方式也只保留一种。

**把每条行内评论立即发送给 Agent。** 用户还没来得及收集相关评论或补充共同指令，就会开始一轮；输入框引用保留用户的选择。

**关闭页签后仍保留评审草稿。** 重新打开同一个 PR 会恢复已放弃的评审状态。页签实例让关闭明确表示丢弃，同时保留切换 Session 的状态。

**暂存代码块或行。** 整个文件已经覆盖“留下或丢弃 Agent 改的某个文件”，只需要四条 Git 命令和一条过期规则。代码块级的写入要把补丁应用到暂存区，还要为位置移动的代码块另定规则；留给以后的变更。

**在 Session 的沙箱策略下执行读者的写入。** 第一版是这样做的，因为 `git add`、`git reset` 和 `git restore` 会运行仓库的 filter，而 Session 可以配置它们。结果是暂存区位于 Session 可写目录之外时按钮都会失败：目录在 checkout 根目录之下的 Session、不是 Host 创建的 linked worktree，以及只读的 Session。2026-11-25 调研的八个同类产品都不约束用户自己发起的 Git 写入，本仓库的归档清理也已经凭用户的授权直接运行 Git。

**为写入置空仓库的 filter driver。** Codex 的 worktree 代码、Reasonix 和 Pi 对每条命令都这样做，本包对读取也这样做。但仓库自己配置了 filter 时（例如只为某个仓库安装的 Git LFS），暂存进去的会是未经 filter 处理的内容，所以使用这类 filter 的文件必须被拒绝。有同样按钮的两个同类产品 MiniMax Code 和 ZCode 执行这些命令时没有这道防护；那三家防护的是其他 Git 操作。能修改仓库配置的 Session 本来就能自己运行命令，所以这道防护会拿走一个可用的功能，却不会去掉任何能力。

**用取消暂存作为暂存的撤销。** 更早暂存过修改的文件，会连那次修改也一起从暂存区丢掉。写入之前的暂存区 tree 能恰好恢复这次写入改动的条目。

**在“未提交”和“分支”范围里写入。** 两者比较的都是工作区，所以暂存不会改变它们显示的内容，只暂存了一部分的文件也看不出是哪一部分。

**把已暂存和未暂存的文件作为同一列表的两组。** 两边都有修改的文件会列出两次，而已审阅标记、展开状态、文件树和跳转都用路径识别文件。

**还原暂存区只登记了路径、还没有内容的文件。** `git restore` 会用空的暂存区条目替换它，而删除它会丢掉用户选择跟踪的文件；视图不为它提供还原。

**自动重试评审写入。** 丢失响应不代表 GitHub 拒绝了请求。保留发出的请求并要求核对，可以避免传输失败悄悄产生重复评论。

**为另一个分支单独设一种视图类型。** 每次读取、透镜请求、已审阅标记的键和数据的键都要多一种情况。本地范围上可选的 `head` 通过它们本来就接受的值到达所有这些地方。

**在菜单里按 Session 列出当前 Session 派出的子 Session。** 每一行用 Session id 指定一个子 Session 的检出。这样每次列出都要读取子智能体目录和每个子 Session 的记录，同一个检出里的多个 Session 需要合成一个标签，Session 后来换了目录时它的行还留在旧名称下。Git 的 worktree 列表通过读者搜索的分支就能到达同样的工作树，不依赖子智能体服务。

**其他分支一律只显示已提交的内容。** 对另一个 worktree 检出的分支只按提交读取，会看不到子智能体尚未提交的修改，而读者正是在子智能体工作时查看这些修改。

**在其他 `head` 上提供写操作和插件条目。** 插槽、注解和 `ctx.forgeChanges` 面向的是 Session 自己的本地变更；其他 `head` 保持只读、不带这些条目，这个接口就不用改。

## Consequences

面板只在打开时显示当前状态；没有任何界面挂载时检查结束不会有通知。Session 之外的改动要等到刷新或下一个工具结果才会出现。本地写操作不记录到 Session，也不告知模型；Agent 下次读取 checkout 时才看到结果。本地写操作会以 Host 的权限运行仓库配置里指定的 clean 和 smudge filter（已对 `git add` 和 `git reset` 实测），而能写自己 checkout 的 Session 可以添加这样的 filter。只有一个远端时，每次检查最多在 Session 的执行环境中启动十二个短暂的 Git 进程；为寻找分叉点每多尝试一个远端，就多启动两个。只有在第一步之前提出请求的 Session 才会有 worktree，失败或被取消的尝试可能留下它的分支或检出。Agent 正在运行一轮或其他维护任务时进入的消息不会被暂留，因此它的 worktree 在第一轮之内创建，已删除的 worktree 也不会被检查。消息等待期间，Agent 以空闲状态处于维护任务中：输入框不提供停止，等待 Agent 空闲的调用方也会一并等待。恢复会丢失从未提交的修改。要求合并队列的基准分支无法从面板合并。组合包挂载两个互不影响的 worktree 服务；模型的工具看不到面板的服务。本地或变更请求的 diff 超过 `maxDiffBytes`，或被托管平台拒绝时，不显示任何文件。展开变更请求中未变更的行时，每个文件只从托管平台读取一次。查看分支的菜单只能按分支找到 Session 所在仓库的 worktree：子 Session 在普通目录或另一个仓库里做的工作不会出现，worktree 以它的分支名出现，而不是以在其中工作的 Session 出现。其他 `head` 在 Session 自己的检出重新读取时才重新读取（点击“刷新”或它自己的变更变化之后），而不是在另一个 worktree 每次修改之后。
