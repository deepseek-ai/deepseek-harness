# Agent Note: PR 评论草稿保存在代码托管平台的待提交评审中

Status: implemented

[English](2026-11-05-forge-pending-review-drafts.md) | 中文

## Problem

[forge 面板](2026-10-09-forge-panel.zh.md)原先把 PR 的评论草稿保存在浏览器页签实例中，作为一次评审发布，并记录已发布的内容。变更视图显示代码托管平台的评审讨论并允许用户回复之后，浏览器草稿留下四个缺口。回复无法加入之后的评审，因为草稿与讨论保存在不同的地方。用户在 GitHub 页面或另一个浏览器中开始的评审不会显示，而用户已有待提交评审时，GitHub 会拒绝直接提交的评审。草稿随页签丢失，在其他设备上也看不到。GitHub 每个用户在每个 PR 上只保留一个待提交评审，两处保存同一个评审会出现不一致。

## Decision

用户留待之后一起提交的 PR 评论，通过提供方的可选能力 `writeReview` 写入代码托管平台上该用户的待提交评审。第一条这样的评论或回复在用户看到的 head 上开始待提交评审，之后的评论或回复加入其中。变更视图随讨论一起读取待提交评审，把其中的评论显示为带“待提交”标签的讨论；“提交评审”带着总结和评审决定提交或丢弃这个评审。回复、解决与取消解决、编辑与删除用户自己的评论也使用同一写操作；写操作会重新检查 head，且从不重试。

浏览器只保存代码托管平台不保存的内容：提交前的评审总结与评审决定、Agent 引用与已发布评论的记录，以及结果有待确认的直接写入。本地变更上的评论本来就没有托管平台上的去处，仍像以前一样进入主输入框。早期面板保存在浏览器中的评论草稿仍可读取：它们作为浏览器草稿显示在对应代码旁，可以加入待提交评审；存在待提交评审时，它们会让“提交评审”保持不可用；没有待提交评审时，“提交评审”像以前一样把它们作为一次评审发布。

在一个私有测试仓库上对 GitHub 的实测确定了三条规则。用户已有待提交评审时，GitHub 拒绝直接创建的评审和单条评论（HTTP 422，“每个 PR 只能有一个待提交评审”），因此视图两者都不提供；不带评审 id 发送的回复仍会加入该评审，因此视图不提供立即回复，提供方也拒绝这种回复。GitHub 拒绝用户批准或请求更改自己的 PR，因此在这种 PR 上，弹窗只提供“评论”。

## Alternatives considered

**把草稿保存在浏览器页签中。** 提交之前不需要写入托管平台，但回复无法加入同一个评审，在别处开始的评审会无说明地阻止提交，草稿也无法随用户换到另一台设备。

**两处同时保存。** 把浏览器草稿同步到待提交评审，或反过来同步，会让一个评审有两个所有者，内容可能分歧，每次编辑都要核对两次写入。

**把草稿记录在 Session 日志中。** 日志记录的是到达模型的内容；评审草稿是模型永远看不到的托管平台状态，同一 PR 上的其他 Session 也看不到它们。

**结果不明时自动重试写操作。** 响应丢失并不能说明 GitHub 是否执行了 mutation。提交待提交评审时，与直接提交一样，这次提交会作为待核对的写入保留下来，在用户到 GitHub 核对之前阻止再次提交；回复、解决讨论或修改评论时，视图重新读取讨论，并请用户核对后再重试。

## Consequences

留待之后提交的评论，在提交前其作者就能在 GitHub 页面上看到，只有用户丢弃评审时才会丢失。每条评论、回复或讨论状态的修改，都消耗一次用于检查 head 的 GraphQL 查询和一个 mutation。解决讨论不会改变 PR 的更新时间，因此面板发出的每个写操作都会丢弃面板保留的讨论；同一 PR 的其他视图在收到下一次状态时，或在 `reviewRefreshMs` 之后显示这一变化。未实现 `writeReview` 的提供方不报告任何写入权限，因此它的讨论保持只读，它的 PR 评论只能立即发布或添加到输入框。早期面板留下的评论草稿会一直保留，直到用户把它们加入评审、发布、删除，或关闭所在页签。
