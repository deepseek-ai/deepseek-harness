# Agent Note：右侧栏拖动样式重算预算

Status: implemented

[English](2026-11-20-rightbar-drag-restyle-budget.md) | 中文

## 问题

在长会话旁拖动右侧栏时，每帧会卡住数百毫秒。Conversation 主体把测得的宽度作为未注册、可继承的自定义属性写在整段记录的祖先元素上，因此即使解析后的正文宽度不变，每一帧也要重算整段记录所有元素的样式；随后读取几何值的 ResizeObserver 又迫使这些工作同步完成。现有浏览器基准覆盖打开、分页和流式输出长会话，但没有一个调整它的宽度，所以这一回归没有门禁。

## 决定

[右侧栏拖动基准](../../../../benchmarks/rightbar-drag-browser/README.zh.md)加入串行浏览器清单。它完整加载一个 120 轮合成会话，打开右侧栏，在 1680×1000 视口中把拖拽条向外拖 40 个 8px 的真实鼠标步再拖回，在两个全新的脚手架环境和浏览器中各做一次。该宽度下正文列始终窄于 680px 的正文宽度下限，每次拖动都会断言这一点，因此拖动改变的是列宽，而不是解析后的正文宽度。

样式重算比值是一个无量纲计数：一次拖动期间所有 `UpdateLayoutTree` 追踪事件报告的元素数之和，除以页面元素数。1680px 用例按方向取上中位数，最多为 1。另一个用例让实际渲染的正文列保持 720px，同时跨越隐藏会话面板的空间预留阈值。其每个方向的比值不得超过 0.10：在 40 步中，即使只有一步重算整段记录的样式，也不能忽略。两种计数都不随 CPU 速度缩放；没有为墙钟终点设置预算，也不将其传给缩放报告。

## 校准

本地 Linux x64 Chromium 样本，每次拖动 40 步：

| 负载 | 加宽 | 缩窄 |
|---|---:|---:|
| 200 轮，宽度轴改动前 | 1,479,947 / 28,895 = 51.2 | 1,909,568 / 28,895 = 66.1 |
| 200 轮，改动后 | 2,622 / 28,895 = 0.09 | 3,368 / 28,895 = 0.12 |
| 120 轮，改动后（两个样本相同） | 2,622 / 18,383 = 0.14 | 3,368 / 18,383 = 0.18 |

改动后重算的元素数在各样本和不同历史长度下完全相同，因此 120 轮时比值留有五倍以上余量，而改动前的行为超出预算五十倍。用例的第一个测试回放这些记录值作为负对照。

在 120 轮负载的 Chromium 追踪中，几何读取修复前每个方向都有 40 次 `Layout` 发生在脚本执行期间，修复后均为 0 次。第二项预算允许每次拖动最多 20 次脚本内布局：它能拦住反复触发同步布局的回归，而不要求每个回调都没有布局，也不惩罚脚本返回后的正常重排。

在 2560px 视口中完整加载 120 轮、正文实际列宽固定为 720px 时，必需基准使用构建后的 Web 产物，追踪包含按下和松开鼠标的整个拖动过程。修复前，加宽方向的重算比值为 18,239 / 18,428 = 0.98974，超过 0.10 的预算。诊断追踪显示，仅一次预留状态翻转就重算了 14,911 个元素。修复后，加宽方向为 380 / 18,428 = 0.02062，缩窄方向为 379 / 18,428 = 0.02057。两个方向的侧栏都移动了 80px，正文列保持 720px，探针均发生翻转。预算允许重算 1,842 个元素，接近两个实测值的五倍；即使没有那次大幅重算，每步重算 82 个元素、连续 40 步也会超限。

正文列固定时，单个完整 `UpdateLayoutTree` 事件最多可重算 512 个元素。在本地 120 轮的加宽追踪中，40 次各重算 1 个元素，40 次各重算 3 个，2 次各重算 4 个，1 次重算 212 个（累计 380 个）。在相同浏览器负载中，只恢复消息流对停靠探针空间标记的继承，小规模重算的分布不变，峰值却从 212 变为 14,911。预算为健康峰值留出两倍以上余量，且不随页面上无关内容的增多而放宽。另一组对照的累计计数同为 600，两者均满足累计预算：分成 200 次、每次 3 个满足峰值预算，集中在一次重算 600 个则失败。

## 备选方案

- 为帧间隔或样式毫秒数设预算。门禁不采用：它们需要尚不存在的浏览器 runner 校准，而且还包含按每个新列宽重排正文的成本，这是缩放本应付出的。它们保留为诊断输出。
- 把拖动加入 `apps/web` 的手动性能通道。不采用：该通道只按需运行，而这一回归必须让 CI 失败。
- 选一个拖动中正文宽度会变化的视口设预算。不采用：继承的宽度变化本来就会重算后代样式，计数测到的会是正文宽度的使用者，而不是这一回归。

## 影响

再次把逐帧变化的输入传给整段记录的回归会在一次基准运行内让 CI 失败，不需要任何计时校准。本用例不为布局或绘制的总成本设限，也不覆盖窗口缩放、Conversation 自身的宽度拖拽条，也不测量停靠的 Session 面板，因为它的末端预留可能在拖动中改变正文内边距。Chromium 的元素计数方式可能随浏览器版本变化；改变计数的升级需要重新记录上面的校准值和负对照中的值。
