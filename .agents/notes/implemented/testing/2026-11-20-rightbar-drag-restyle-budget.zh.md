# Agent Note：右侧栏拖动样式重算预算

Status: implemented

[English](2026-11-20-rightbar-drag-restyle-budget.md) | 中文

## 问题

在长会话旁拖动右侧栏时，每帧会卡住数百毫秒。Conversation 主体把测得的宽度作为未注册、可继承的自定义属性写在整段记录的祖先元素上，因此即使解析后的正文宽度不变，每一帧也要重算整段记录所有元素的样式；随后读取几何值的 ResizeObserver 又迫使这些工作同步完成。现有浏览器基准覆盖打开、分页和流式输出长会话，但没有一个调整它的宽度，所以这一回归没有门禁。

## 决定

[右侧栏拖动基准](../../../../benchmarks/rightbar-drag-browser/README.zh.md)加入串行浏览器清单。它完整加载一个 120 轮合成会话，打开右侧栏，在 1680×1000 视口中把拖拽条向外拖 40 个 8px 的真实鼠标步再拖回，在两个全新的脚手架环境和浏览器中各做一次。该宽度下正文列始终窄于 680px 的正文宽度下限，每次拖动都会断言这一点，因此拖动改变的是列宽，而不是解析后的正文宽度。

预算是一个无量纲计数：一次拖动期间所有 `UpdateLayoutTree` trace 事件报告的元素数之和，除以页面元素数，按方向取中位数，最多为 1。每帧都重算整段记录的拖动大约每帧就达到一倍；修复后的拖动总计远低于一倍。该计数与 CPU 速度无关，因此既不使用共享的时间缩放系数，也不使用波动余量；没有为任何墙钟终点设预算，也不把它们传给缩放报告。

## 校准

本地 Linux x64 Chromium 样本，每次拖动 40 步：

| 负载 | 加宽 | 缩窄 |
|---|---:|---:|
| 200 轮，宽度轴改动前 | 1,479,947 / 28,895 = 51.2 | 1,909,568 / 28,895 = 66.1 |
| 200 轮，改动后 | 2,622 / 28,895 = 0.09 | 3,368 / 28,895 = 0.12 |
| 120 轮，改动后（两个样本相同） | 2,622 / 18,383 = 0.14 | 3,368 / 18,383 = 0.18 |

改动后重算的元素数在各样本和不同历史长度下完全相同，因此 120 轮时比值留有五倍以上余量，而改动前的行为超出预算五十倍。用例的第一个测试回放这些记录值作为负对照。

## 备选方案

- 为帧间隔或样式毫秒数设预算。门禁不采用：它们需要尚不存在的浏览器 runner 校准，而且还包含按每个新列宽重排正文的成本，这是缩放本应付出的。它们保留为诊断输出。
- 把拖动加入 `apps/web` 的手动性能通道。不采用：该通道只按需运行，而这一回归必须让 CI 失败。
- 选一个拖动中正文宽度会变化的视口设预算。不采用：继承的宽度变化本来就会重算后代样式，计数测到的会是正文宽度的使用者，而不是这一回归。

## 影响

再次把逐帧变化的输入传给整段记录的回归会在一次基准运行内让 CI 失败，不需要任何计时校准。本用例不测量布局或绘制成本、窗口缩放、Conversation 自身的宽度拖拽条，也不测量停靠的 Session 面板，因为它的末端预留可能在拖动中改变正文内边距。Chromium 的元素计数方式可能随浏览器版本变化；改变计数的升级需要重新记录上面的校准值和负对照中的值。
