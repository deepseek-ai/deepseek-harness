# Agent Note: 仅等待收件箱的 Agent 等待

Status: implemented

[English](2026-10-29-inbox-only-agent-wait.md) | 中文

## 问题

任务板提交改变共享状态，但不向成员投递输入。每次编辑都结束所有成员的等待，会使普通 subagent 控制依赖 Team 协调，并让调用者在没有消息说明需要关注什么时恢复执行。

## 决策

`wait_agent` 仅通过现有插入事件观察当前调用者自己的下一步收件箱。它先订阅再检查待处理输入，不消费输入，并在输入到达、超时、取消、调用者释放或工具卸载时移除监听器和定时器。排队的下一轮输入、其他 Agent 的活动和任务板变化不会结束等待。

任务命令追加并刷盘修订，不通知等待者，也不写入收件箱消息。需要成员处理更新时，调用者发送明确消息。不新增 Agent 方法、共享等待服务或任务专用等待事件。

这仅取代[Team 任务板](../architecture/2026-10-19-team-task-board-inbox.zh.md)中的等待信号决策。树权限、持久任务存储、历史记录不授予权限及与普通控制工具分离的决策仍然适用。不改变 Session 事件代次。

## 考虑过的替代方案

**每次任务提交后通知所有当前等待。** 这避免了重复收件箱状态，但仍让无关任务编辑打断每个等待成员。将通知移到服务方法后仍保留该行为和耦合。

**将每次任务变化持久化为消息。** 任务日志已经保留修订；逐成员通知增加未读状态和投递恢复。明确消息可以表达哪些更新需要行动。

**在 Agent 或收件箱中增加等待。** 现有输入事件和工具拥有的取消机制已能实现所需等待，无须扩展核心 API。

## 后果

仅更新任务不会恢复等待中或空闲的成员。需要继续工作时，调用者必须通信。工具不返回任务内容；成员按需查询任务板。等待前和等待期间发生的任务变化效果相同：都不影响等待。

单元测试覆盖已有输入、调用者隔离、并行等待、取消、释放，以及不结束等待的任务提交。任务板录制场景检查过去和并发提交下的等待超时，完成通知仍作为普通收件箱输入。
