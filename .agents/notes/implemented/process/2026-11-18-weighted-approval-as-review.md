# Agent Note: Weighted approval gains a machine-account review pilot

Status: implemented

English | [中文](2026-11-18-weighted-approval-as-review.zh.md)

## Problem

The required `weighted approval` commit status keeps the approval decision inside the CI check group. It stays `pending` until the policy holds, so an approval wait looks like running CI, and it duplicates the repository's native review requirement. Issue #6719 records that a later `pull_request_target` run can leave the merge box at `Expected` while the API reports `success`.

The earlier [decision about the commit status](../../archived/process/2026-10-20-weighted-approval-status-gate-with-check-run-label.md) kept the status because a required check run could not be associated reliably with the pull-request head. Replacing the status directly would remove the only enforcement of the two-point policy before a review-based requirement is verified. A GitHub App identity cannot satisfy a team-based required reviewer, because an App installation is not a team member, and minting an App token adds a private key to every evaluation.

## Decision

The commit status requirement stays in place during a staged rollout. The legacy `weighted-approval` workflow keeps publishing the `weighted approval` commit status and the `weighted approval decision` check run at their existing paths, and active ruleset 20925054 keeps requiring the status and one approving review. The machine review can satisfy that review count but not the status, which still blocks a pull request below the weighted threshold. The status uses the job token; the decision label prefers a check run owned by the configured App slug. If minting the App token fails, the job token is the fallback for the label, and a label failure does not remove the required status. The legacy publisher remains the sole writer for delegated human-review dismissals and review requests.

A second workflow, `weighted-approval-machine`, publishes the same decision as a marked status comment and a native approving review; the comment is authored by `github-actions[bot]` and the review by the machine account `deepseek-ai-harness` (user ID 359032549). It reuses the scoring policy and the no-permission `weighted-approval-review-event` workflow handoff. Its job token has `contents: read`, `pull-requests: read`, and `issues: write`; it reads the other reviews, comments, permissions, and history needed for scoring and writes the status comment as `github-actions[bot]`. Its PAT writes only the approving review and the dismissal of that approval. It never dismisses a human review or requests review.

The job token reads every repository input the pilot needs (the pull request, reviews, comments, permissions, merged history, production ownership, and the current review state) and maintains the marked status comment, which GitHub attributes to `github-actions[bot]` (user ID 41898282). The PAT is used only for the `/user` identity check and for submitting or dismissing the pilot's marked reviews. The `evaluate` job declares `environment: weighted-approval` as a literal; that fixed environment supplies the value. The reusable workflow's `workflow_call` declares `DSH_APPROVAL_BOT_TOKEN` with `required: true`, and the legacy publisher that calls it forwards only the name (`DSH_APPROVAL_BOT_TOKEN: ${{ secrets.DSH_APPROVAL_BOT_TOKEN }}`), not `inherit`. The caller must pass the name even though the called job's environment supplies the value; an environment secret takes precedence over a same-named repository or organization secret. The standalone triggers are unchanged: their `evaluate` job declares the same environment and reads the secret directly. The environment's deployment branch policy allows only `master`, has no tag rule, and disables administrator bypass; a deployment that does not satisfy it is rejected before the job's steps run. `required: true` fails a caller that omits the secret but does not prove the environment secret has a value. [Passing inputs and secrets to a reusable workflow](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows) documents the name-only pass and the environment precedence. The pilot mints no App token and holds no App private key. Before a review submit or dismissal it verifies by `/user` that the PAT belongs to the machine account by numeric user ID and login; a missing or wrong value fails the run before that write. The pilot identifies its status comments by the `github-actions[bot]` user ID with the marker on the first line, and its reviews by the machine account user ID, so a copied marker from another account is ignored. The `github-actions[bot]` account is shared with other repository workflows, which is why the first-line requirement exists; a comment created earlier by the machine-account PAT is not recognized, updated, or deleted. Both publishers exclude the machine account's review from scoring.

The pilot publishes:

- An unmet policy creates or updates one comment marked `<!-- weighted-approval -->` with the job token. The comment lists the score, counted approvals, remaining points, blocking change requests, delegated reviews still awaited, and reviews without write access.
- A met policy submits an `APPROVE` review for the evaluated commit with the same marker using the PAT, and deletes that comment only after the review is recorded. A failed submission leaves the comment in place. The publisher submits no second review when its latest review is already `APPROVED` for that commit.
- A draft retracts every marked machine-account `APPROVED` review and removes the comment; drafts are never approved. A blocking change request or a score below the threshold also retracts those reviews and then posts or keeps the comment.
- Before submitting an approval it re-reads the pull request with the job token and fails when it closed, became a draft, or the head changed. The review carries the evaluated commit ID, and the pilot verifies that the returned review names it.

The pilot does not dismiss its approval before evaluating, because dismissing it would itself be a review event and start another evaluation. When a review write is required, the pilot first verifies the PAT's identity: before submitting an approval, and before dismissing a marked approval during retraction. A missing or wrong PAT fails the run before that write. When a previous marked approval must be dismissed, that failure happens before the publisher updates or deletes the status comment, so the old approval and comment remain. After identity verification, a scoring failure attempts to dismiss every marked machine-account approval and then fails the run. Setup, credential, or API failures and undelivered events can still leave an earlier approval, so a prior approval can survive those paths. Stale-review dismissal stays off in rulesets 20925054 and 27532727, so a push after publication does not retract the approval; the next evaluation re-scores the new head. An explicit dismissal while the policy still holds starts an evaluation that submits a new approval for the current head. Workflow runs are asynchronous, so a pull request can briefly show an approval for an earlier commit. These are pilot limitations; the required review team is not enforced until error behavior, latency, and stale-approval behavior are addressed and verified.

Publication is controlled by `DSH_APPROVAL_REVIEW_SCOPE`: unset disables the pilot; an exact decimal pull-request number publishes only that pull request; `all` publishes open pull-request events broadly. A `workflow_dispatch` input `pull_number` re-evaluates one open pull request from the default branch when the scope selects it. Ruleset 27532727 stays disabled during the pilot and adds no separate requirement. The active ruleset 20925054 requires one approving review and the `weighted approval` status; the machine review satisfies the one-approval requirement, but a pull request below the weighted threshold stays blocked by the status.

After the pilot verifies comment updates, approval submission, dismissal, head binding, error behavior, latency, and stale-approval behavior, re-evaluate every open pull request the requirement will cover and inspect its published comment or approval. Configure an isolated ruleset on a disposable branch whose include condition names only that exact branch, add a team whose only member is the machine account as required reviewer for all files with `minimum_approvals: 1`, and validate root files, dotfiles, and nested files with pull requests; do not add the team to rulesets 20925054 or 27532727 for the test, do not apply the test ruleset to production branches, and delete it afterward. After that verification, add the same team to ruleset 27532727 with the file patterns for the files the requirement covers, and enable the ruleset. That requirement makes the machine account's approval mandatory. Only after that team requirement is verified does the rollout retire the legacy status requirement and publisher. Neither is removed before then.

## Verification

The approval policy suite runs keyless tests with `pnpm run test:approval-policy`, covering both publishers: legacy status publication; workflow-comment identity by the `github-actions[bot]` account and first-line marker; approving-review publication and dismissal with the machine PAT; the read/write token split, its lazy identity verification, and credential failures; retraction; scope selection; machine identity; head binding; delegation; scoring; and API failures. The workflow test in `scripts/ci-workflow.spec.ts` pins the trusted checkout, the no-permission review-event handoff, the legacy status and App label tokens, the literal `weighted-approval` environment on the evaluate job, the required `workflow_call` secret declaration and the caller forwarding only its name, the machine workflow's `contents: read`, `pull-requests: read`, and `issues: write` permissions and the caller's matching grant, the absence of App token minting in the pilot, the scope variable, the workflow-dispatch input, the events, and the commands.

The merged #9005 probe measured environment isolation only for manual `workflow_dispatch` runs against a dedicated probe environment: its protected job read the marker secret at `master`, the same job was rejected before any step at a topic branch, and a separate control job without the environment ran at the topic branch and asserted the marker absent. It did not measure `pull_request_target`, `workflow_run`, or the delegated `workflow_call` from the legacy publisher. Before the pilot covers a second pull request, verify on one isolated pull request that the `evaluate` job reaches the `weighted-approval` environment and reads `DSH_APPROVAL_BOT_TOKEN` on each of those three paths. Confirm each run records a deployment for that environment and completes the write for its evaluated state: the job token's status comment, or the identity check and approving review from the PAT. Set the scope to that pull request's number for the test and do not set `all` until all three pass.

The live rollout is staged and is not performed by this change: this change does not set the variable, enable ruleset 27532727, or remove the legacy status requirement. The first live attempt on pull request #9313 reached the protected job with a nonempty PAT, but a pull-request read returned 404 before the identity check, so the run published no comment and no approval; the scope was unset afterward. The 404's cause is not established, and no run has published a machine-account approval with this credential split, so a planned run is not evidence that the review write succeeds. Before enabling coverage, set `DSH_APPROVAL_REVIEW_SCOPE` to one pilot pull-request number with two approval points and confirm that the machine account submits one `APPROVE` review whose `commit_id` is the current head and whose `user.id` is 359032549, that the status comment appears as `github-actions[bot]`, and that the comment disappears; a `reviewDecision` of `APPROVED` alone does not show who approved or for which commit. A pull request below two points keeps the comment and has no machine-account approval. Then set the variable to `all` and verify the same behavior on open pull-request events. Re-evaluate every matching open pull request before enforcing the team requirement. Only after the required review team is configured and its error behavior, latency, and stale-approval behavior are verified, retire the legacy status.

## Alternatives considered

**Replace the commit status directly.** Rejected because it removes enforcement before a review requirement is verified; ruleset 27532727 is disabled and the required review team is not verified.

**Publish the review with a GitHub App.** Rejected because an App installation cannot join a team, so it cannot satisfy the future singleton-team required reviewer, and every evaluation would mint a token from a private key.

**Keep the pilot PAT as a repository or organization secret.** Rejected because any user with write access could push a branch whose modified workflow reads that secret without an environment; the environment-scoped copy is unavailable to a job that does not declare `weighted-approval`, and that environment admits only `master` deployments.

**Keep the commit status permanently.** Rejected because the status stays a CI entry that blocks merges and can show `Expected` (issue #6719); the pilot exists to replace it after verification.

**Publish the pilot without the scope restriction.** Rejected because an unexpected comment or review state would reach every pull request; the scope variable limits exposure to one pilot pull request and then to `all`.

**Let the pilot reconcile delegated dismissals and review requests.** Rejected because two publishers would write the same human reviews; the legacy publisher remains the sole writer during coexistence.

**Require the singleton team from the first rollout.** Rejected because a pilot failure would then block every pull request; the team requirement waits for verification.

## Consequences

During coexistence, the active one-review requirement can be satisfied by the machine review while the required status still blocks a pull request below the weighted threshold. Ruleset 27532727 and the team requirement add no enforcement until enabled. A scoring failure attempts to dismiss the pilot's approval, but setup, credential, or API failures and undelivered events can leave an earlier approval standing; a push after publication can also leave an approval for an earlier commit until the next evaluation. Reviewers must check the reviewed commit.

The status comment is written with the job token under `github-actions[bot]`, and every repository read uses that token; the PAT is kept for review writes only. The pilot's first live target, pull request #9313, had no machine-account status comment, so the change in comment ownership required no migration. A comment created earlier by the machine-account PAT would remain in place because the publisher no longer recognizes that account's comments. The PAT's review writes remain subject to the machine account's repository grant, and the pilot does not promise that GitHub permits them. The caller job adds only the `issues: write` grant; its call, filters, and name-only secret forwarding stay the same, and the legacy publisher's behavior is unchanged.

The machine account needs write access to the repository. Its PAT must be rotated and stored only as the `weighted-approval` environment secret `DSH_APPROVAL_BOT_TOKEN`; the repository scope must not carry a copy, and this repository's access to a same-named organization secret must be removed, because a job without the environment could read either copy. This is broader access than the App installation used for the legacy check-run label. GitHub rejects an approval of a pull request the machine account authored. After the singleton-team requirement is enabled, a human approval cannot satisfy that requirement, so machine-authored pull requests must not target covered refs.

After the team requirement, the machine account's approval is mandatory and the weighted score decides the merge requirement for every pull request; any write-capable human approval no longer satisfies the requirement by itself. Retiring the status then removes the `Expected` failure mode from later `pull_request_target` runs. The legacy publisher's job is no longer required; a failed pilot evaluation appears as a failed run without blocking a merge that already has the required team approval.
