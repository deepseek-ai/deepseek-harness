# Agent Note: Serve Computer Use to other harnesses as an MCP server

Status: implemented

English | [中文](2026-11-09-computer-use-mcp-server.zh.md)

## Problem

Computer Use training data should come from several agent harnesses, not only from DSH sessions. Codex, Claude Code, and in-house harnesses connect to capabilities through MCP stdio servers; Codex's own Computer Use is a stdio server with a persistent JavaScript REPL. DSH's `cua_run_code` already composes a retained program environment, consent, screenshots, and native connections per Agent, but only a DSH model turn could call it. The MCP form must keep those owners, persist program state across calls, and start from one documented command on every DSH distribution.

## Decision

`@deepseek-ai/dsh-cua-mcp` is an experimental bundle in `OPTIONAL_BUNDLES` that composes the standalone `cua-mcp` profile from one insert over the empty root. A profile manifest that selects it as the only bundle is the whole installation step: the launcher loads an existing manifest without consulting `PROFILE_TEMPLATES`, and the installation already ships the bundle, so no pnpm or registry access is involved. It is the only MCP application path; no package bin or SDK escape exists, and the bundle stays out of `PROFILE_TEMPLATES` because templates cannot name experimental packages.

The server runs inside the profile process and calls `ctx.tools.execute` with the connection's Agent and no model step. One stdio connection owns one Agent: creation before the stdio transport opens, disposal at stdin EOF. Each program call runs as that Agent's maintenance activity, so Agent disposal cancels an in-flight call and waits for it and its nested calls before the Session closes. Agent ownership already selects the retained program process, native connection, and session-scoped grants, so connection lifetime and state lifetime coincide. The empty default preset `cua-mcp` composes no model-facing rows, and the provider gives that Agent `cua_run_code` because it is not on the preset named by `agentPreset`. The Agent works in a dedicated workspace, `DSH_CUA_WORKSPACE` or `cua-mcp/workspace` under the Harness home: an Agent's working directory is the `workspace-write` root of its programs, and the directory a client launches the server from can be `/`.

Three tools form the surface. `cua_run_code` is the Agent's DSH registration served through the protocol server's low-level `tools/list` and `tools/call` handlers: each listing projects name, description, and parameters from the tool registry, and a call passes its arguments to the tool executor unchanged inside the Agent's initiator scope, so the provider's definition is the only schema, `description` is required as that definition declares, and validation and unknown names are answered by DSH; the one trim is the registration's sandbox-escalation fields, which the projection omits and a call may not name. `cua_get_api_reference` returns the `cua` API reference, the provider's guidance registered for the Agent, and keeps no state, so any conversation on the connection can read it at any time. `cua_reset` ends the Agent's program environment and keeps the Agent: the frontend cancels the running program and calls `ctx.cuaPrograms.release`, with which the provider's program runtime releases the environment of that state owner and which the CUA provider exposes beside `screenshotRequestTarget`; the next program starts a fresh process, while the native connection and the session's consent decisions stay. The frontend orders its own calls around the release: a reset answers after the cancelled program has settled, and programs wait for a release in progress. The projection delivers each inspected screenshot as the request version the program observed, so coordinates in program text match the delivered image. The provider's new `screenshotTarget` configuration replaces the model-route lookup that a profile without a model cannot satisfy.

Consent has two modes. `DSH_CUA_CONSENT=allow` answers every approval question of the connection's Agent with its approving label for the session. The default `elicit` forwards each question to the client as a form elicitation whose enum is the question's labels. No Session event is added: the training side consumes MCP tool results, and the connected harness's transcript records calls; DSH retains nested `tool/ptc-dispatch` events for diagnosis.

The composition lists its dependency closure, twenty-six rows, instead of layering on `dsh-base`: no model adapter, prompt-side tool, telemetry, or session-management row loads. `cua-mcp` is not a required startup entry, so a row that cannot activate is reported by the launcher on stderr: an inactive provider leaves `cua_run_code` out of the listing, and an inactive frontend serves nothing. Client entries are documented in the README instead of generated.

## Alternatives considered

**An MCP server that launches `dsh --profile sdk` through the TypeScript SDK.** The SDK protocol has no request that runs a tool without a model turn; adding one changes the protocol and both SDK clients, and screenshots would cross a second process boundary.

**A standalone CUA server outside the harness, like Codex's REPL.** Consent, sandboxing, logging, screenshot admission, and helper lifecycle would be rewritten. The in-profile server reuses those owners and remains the basis for a later extraction.

**A `turn_ended` hidden tool with client hooks.** Its only use would be writing the client's turn boundaries into a log nobody consumes; held keys already release when a program settles.

**Session events for root MCP calls.** The data consumers need only MCP results; a `tool/call` without a model step would invent a step the Session never ran.

**Exposing the raw `cua` tool or program sandbox escalation.** Raw operations need per-method schemas the external model would relearn, and escalation needs an approval answerer the profile does not have.

**A profile frontend layered on `dsh-base` with model rows disabled.** The composed profile carried about a hundred rows without a consumer: model adapters, web tools, subagents, compaction, telemetry, and session management. The explicit closure is a quarter of that and fails loud on drift.

**A `dsh plugin enable|disable` subcommand that selects the shipped bundle.** It duplicated the plugin manager's manifest-only selection inside the launcher and still produced a base-backed profile; the documented manifest is three lines and needs no launcher change.

**A `dsh.bundle.profile` declaration that app-boot initializes on the first `dsh --profile cua-mcp`.** It made the first start zero-step, at the price of a new manifest field and a `shippedProfileTemplate` lookup in app-boot, the CLI `dsh plugin` command, and the plugin manager for one experimental bundle; the plain manifest costs one documented step and leaves those packages untouched. Once CUA graduates from experimental, a `PROFILE_TEMPLATES` entry gives the same zero-step start.

**A hand-written MCP schema and description for `cua_run_code`.** The second copy drifted within days: 663 against 2,164 characters of description and an optional against a required `description`. Projecting the registration removes the copy; the SDK's `registerTool` accepts only Standard Schema values and refuses to share `tools/list` and `tools/call` with custom handlers, so both tools use the low-level handlers.

**The `cua` API reference inside the tool description or the server instructions.** Claude Code 2.1.309 forwards the first 4,096 characters of an MCP tool description, and of the server instructions, and appends `… [truncated]`, measured on 2026-11-10 with 20,000-character probe texts; `dsh-mcp-client` forwards the same description intact. The reference is about 13,000 characters, so it travels as a tool result, and the registration's 3,200-character description stays within the budget.

**The reference at the head of the first program result of each environment.** The server cannot observe which results a model keeps: a client such as `dsh-mcp-client` holds one connection for several conversations, a cancelled or failed first call discards its result, and context compaction drops the text later. The flag that recorded delivery was written by program calls and by resets without a common ordering point. A read tool without state lets the model that lacks the reference ask for it; in fifteen probe conversations on 2026-11-11, through `dsh-mcp-client` with a DeepSeek model and through Claude Code 2.1.309, every model called it before its first program.

**A reset operation on the PTC program-tool factory.** A factory handle with `reset(agent)` made the tool executor a second owner of environment recovery, with its own blocked state after a failed cleanup. The program runtime's owner release already ends an environment, and the next run for the same owner starts a new one; the frontend serializes the connection's calls, so it is the caller that orders them around the release.

**Replacing the connection's Agent on reset.** A new Agent has a new Session: the native connection closes, session consent is asked again, and a refusal is forgotten, which is what reconnecting does. A reset discards what programs hold; consent and the native connection belong to the connection and are no part of the program environment. Disposing an Agent also waits for the runtime's stop grace, three seconds by default, when the running program cannot be interrupted.

**A `--print-client-config codex|claude-code|json` option.** Rendering the exact command of an installation needs `node:sea` to tell a single-file executable from a script launch, and the browser worker image, which packs every optional bundle, registers no `node:sea`; the documented entries carry the same timeouts and output budget without that dependency.

## Consequences

Every installation carries the bundle; its native providers, macOS and Windows, are optional dependencies, each mounted by a row that loads only on its own Host, and `verify-default-product-isolation` keeps the bundle out of default templates. A profile that layers the bundle over `dsh-base` duplicates row ids and is unsupported; the Web plugin page hides the bundle through `HIDDEN_BUNDLES` while the Host inventory still reports it as optional. Hosts without a provider list `cua_get_api_reference` and `cua_reset`, which both name the missing provider, and a `cua_run_code` call fails as `unknown tool`. Clients see state loss on process exit, `cua_reset`, or Agent disposal and recreate objects. Consent elicitation depends on the 2025 MCP request model; clients on the 2026-07-28 revision use `allow`. The tool descriptions, the server instructions, and the reference text are pinned by the profile's expected-output test; the program description and the reference change with the installed CUA packages. A model receives the reference only by calling `cua_get_api_reference`, so a client that withholds that tool leaves it with the execution rules alone. A provider description longer than 4,096 characters reaches Claude Code models cut.
