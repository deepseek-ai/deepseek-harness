# Agent Note: 按权限属性判断自动电脑操作授权

Status: implemented

[English](2026-11-26-cua-permission-attributes.md) | 中文

## 问题

Windows 启动器与拥有窗口的应用可能具有不同的原生应用 ID。飞书的开始菜单条目 `com.electron.Feishu` 启动 `Feishu\Feishu.exe`，窗口却属于 `Feishu\app\Feishu.exe`，且没有显式或打包应用 AUMID。只比较一个授权 ID 会让同一产品重复请求授权。按发布者、目录或进程祖先推断关系，又可能合并用户希望分别授权的程序。

## 决策

应用授权比较权限属性集合。每次选择时，提供方报告现有授权 ID 和可选的命名属性值。[共享匹配器](../../../../packages/experimental/cua/src/application-identity.ts)在同名属性存在共同非空值时，将选择与已保存记录视为同一权限对象。匹配成功或保存决定后，观察到的值会加入该记录，因此后续观察即使与第一次观察没有共同值，也可以通过中间观察补充的值匹配。通过共同值关联的记录在权限页、撤销和“允许再次询问”中作为一组处理。匹配只扩大识别范围：会话授权仍只适用于当前会话，只有明确选择“始终允许”才保存跨会话授权。

macOS 是单属性情形。其辅助程序报告现有的 [bundle ID 或规范可执行文件路径摘要](2026-10-25-cua-bundle-id-consent.zh.md)，不提供其他属性，因此授权匹配与原来完全相同。

Windows 保留原有应用发现规则：窗口的原生 ID 依次取显式 AUMID、打包应用的进程 AUMID 和可执行文件路径，只有相同 ID 才合并。`getApp` 另外报告所选条目、其窗口、窗口所属包和 Shell 给出的 AUMID，以及所选窗口的可执行文件路径。[包参考文档](../../../../packages/experimental/cua-windows/README.zh.md#permission-attributes)维护属性规则。Shell 属性值来自未公开的 Windows 8+ `IApplicationResolver`，仅为授权在 STA 线程查询；查询失败时不提供属性值。应用发现、窗口归属和启动等待从不使用权限属性。

窗口首次接纳时检查应用关联。已接纳的 HWND 在有效期间保留该关联。helper 不保留目标 PID 或进程启动时间，也不在每次操作前重复检查应用身份。

记录在 [profile 授权存储](2026-10-19-cua-profile-consent-storage.zh.md)中保留原有授权键。[共享应用授权执行](2026-09-26-cua-application-consent.zh.md)仍在每次原生操作前检查句柄绑定的记录。

## 考虑过的替代方案

**维护产品启动器与运行文件布局名单。** 将特定路径映射到开始菜单 ID 只覆盖名单中的产品，依赖对每种安装布局的先验知识，还会改变原生发现 ID 和启动目标。

**按发布者、安装目录或进程祖先归组。** 同一个发布者或目录可以包含独立应用；启动另一个进程不代表已同意访问它。

**将多个标识拼成一个键，或要求全部属性相同。** 只要有一个值不同，两种做法都会把启动器和运行程序分开。

**只使用公开 API。** 窗口属性存储、包 API 和应用诊断都无法为飞书未打包的运行程序提供共同值；只有 Shell 解析器能将它与开始菜单 ID 关联。

**保留 PID 和进程启动元数据并反复验证归属。** 这为已接纳 HWND 引入另一套应用生命周期模型和额外的进程查询。本实现采用 Windows 句柄有效性。

**将关联记录合并为一条存储记录。** 已有句柄和其他进程引用原记录键；分组操作保留这些键。

## 后果

属性用于权限分组，不认证发布者。声明了已授权 AUMID 或位于已授权可执行文件路径的应用会共享该授权。撤销后已学习的属性值仍保留，因此之后的决定作用于整组记录。拥有共同属性的版本和副本有意共享授权；没有共同属性的选择仍需分别授权。

共享授权不关联窗口。启动器与运行程序仍是独立的原生应用对象：启动器句柄不能操作运行程序的窗口，对启动器调用 `app.launch()` 时，仍可能因等待其自身 ID 的窗口而超时。

新增属性来源需要证明其值标识同一产品，且不得来自名称、图标、发布者、目录或进程祖先。测试覆盖经中间观察的匹配、属性名隔离、会话范围、分组撤销、并发选择、重启后保留，以及真实桌面运行中发现 ID 和已接纳 HWND 保持不变。
