# Agent Note: Forge 状态简报

Status: implemented

[English](2026-11-12-forge-status-briefs.md) | 中文

## Problem

会话列表为每个已列出 Session 绑定的变更请求显示一个状态图标，此前为此读取每个变更请求的完整快照：最多 100 个检查 context、评审人、评审讨论、关联 issue 以及仓库的合并设置。注册表把同一个 forge 所有到期的变更请求合成一批，GitHub 提供方此前把一个主机的整批放进同一个 GraphQL 查询。GitHub 在处理一个请求超过 10 秒后终止它：包含 20 个 deepseek-harness pull request 的快照查询耗时 10.2 s，30 个的返回 HTTP 504，61 个的返回 HTTP 502。列表每次新的运行会让所有监听同时到期，所以绑定了约 30 个 pull request 的用户，列表会整批失败、整批重试。打开一个 Session 时，如果列表已经在监听它的变更请求，就不会触发任何读取，面板最长要等一个空闲间隔才有更新的状态。

还有一些读取是不必要的重复。变更请求只有在同一毫秒到期时才共用一次读取，所以 14 个列表监听在保持对齐时每小时 30 个查询，错开之后是 415 个。每次重新显示 Session 的面板，Host 都重新检查登录状态、重新按分支查找，客户端还会强制再读一次状态。每保存一个已审阅标记，所有打开的变更视图都会重读全部标记和全部评审讨论。Agent 的推送或 `gh pr merge` 不会触发状态读取。

## Decision

**两个层级的状态。** 简报包含列表显示的内容：标题、状态、草稿标记、可合并性、评审结论与检查汇总结果。`ctx.forge.watchBrief` 监听简报；`ctx.forge.watch` 监听快照。被监听的变更请求在有快照监听方时轮询快照，否则轮询简报。快照包含简报，所以简报监听方能收到每一次结果。提供方通过可选的 `fetchBriefs` 读取简报；提供方没有该方法时，注册表从它读取快照。

**GitHub 简报查询。** forge-github 从 pull request 自身的标量字段和 head 提交的 `statusCheckRollup.state` 读出简报，每个查询 25 个 pull request（`briefBatchSize`）。通过 `gh` 在 deepseek-harness 的 pull request 上实测，10 个的查询用 1.6 至 2.0 s，25 个的用 2.5 至 3.4 s，50 个的用 2.9 至 6.8 s，速率配额各消耗 1 点；25 个比 50 个离 GitHub 的 10 秒上限更远。快照查询里检查 context 占比最大：8 个 pull request 时占 186 KB 中的 174 KB、3.8 s 中的 1.4 s。

**大小有上限的 GitHub 快照查询。** 一个 Session 可以绑定多个 pull request，它的面板监听其中每一个的快照。forge-github 在一个快照查询里最多放同一主机的 8 个 pull request（`snapshotBatchSize`）：用同样的方式实测，5 个的查询用 3.6 s，8 个的用 4.4 至 6.3 s，10 个的用 5.8 s。查询依次发送，因为 GitHub 要求同一账号串行发送请求。某个查询的 `gh` 运行失败或被 GitHub 拒绝时，只有该查询内的 pull request 失败。

**每个查询一次提供方调用。** 提供方可以向注册表声明 `snapshotBatchSize` 与 `briefBatchSize`，forge-github 声明了这两项。这时注册表为同一主机每这么多个到期的变更请求调用提供方一次，依次调用，每次调用有自己的 `fetchTimeoutMs`，并在调用返回时结算它的监听。某次调用失败或超过时限时，只有它读取的变更请求失败，之前各次调用的结果保持已发布。没有声明大小的提供方（如 forge-gitlab）仍然一次调用读取该 forge 所有到期的变更请求。

**每个 forge、每个层级同时只有一次读取。** 为打开的面板读取快照，不用排在长列表的简报读取后面；一个主机同时最多看到同一个注册表的两个状态请求。

**共用一次读取的轮询。** 一次读取除了读它的 forge 和层级上到期的变更请求，还读距上一次状态的等待已过半的变更请求。所以在不同时刻到期的变更请求会回到同一次读取里：14 个列表监听在此前的间隔下每小时 30 个查询，不论它们是同时绑定、逐个绑定，还是中途有检查运行过一阵。读取失败后的退避时间，变更请求会完整等完。

**间隔。** 打开状态的变更请求在检查运行时每 15 秒轮询一次，否则每 60 秒一次（`activeIntervalMs`、`idleIntervalMs`），两个层级相同。状态第一次报告可合并性未知时，按活跃间隔再轮询一次；再次报告未知时等待空闲间隔，因为实测的 98 个打开的 pull request 里有 11 个一直报告未知，它们都是叠在另一个 pull request 分支上的草稿。

**列表已经知道的状态。** 列表的运行把它为变更请求存下的状态作为 `known` 传入。注册表按“在 `known.fetchedAt` 读过一次”来安排首次轮询，所以已合并的变更请求不再读取，同一进程里紧接着的下一次运行会等到间隔到期。读取时间只保存在内存中；更早的进程存下的状态按在纪元时刻读取处理。

**比最近一次更新的状态。** 快照监听方和 `refresh` 都可以传入 `maxAgeMs`。会话面板和评审页开始时传入 `statusMaxAgeMs`（10 秒），所以打开 Session 会立即读取它的变更请求，除非刚刚读过；再次显示面板和窗口获得焦点时调用 `revisit` Remote，它按同样的上限轮询，读者手动刷新则仍然强制读取。两个同类产品已安装的桌面应用也是这样做的：Codex 在线程挂载且数据超过 15 秒时重新读取它的 pull request，Claude 在会话行被按下时预读它的 pull request，新鲜期为 10 秒。

**Agent 的命令之后的读取。** 收到推送结果后，forge-session 为被推送仓库里可见的变更请求调用 `ctx.forge.expectChange`：被监听的变更请求立即轮询，之后按活跃间隔轮询，直到状态报告检查正在运行为止，最长持续一个空闲间隔。有过工具结果的回合结束时，forge-session 刷新该 Session 可见的变更请求，以那个结果距今的时间作为 `maxAgeMs`。

**不为隐藏的页面读取。** 页面隐藏满 30 秒后，客户端关闭面板流、列表的状态流和评审计数流，页面再次显示时重新打开。Host 只在有流打开时轮询，所以不需要页面上报可见性；只要页面有一个标签页可见，它就继续轮询。

**在关注方之间保留面板状态。** Session 的面板在最后一个关注方离开时留下它最后的状态、快照和分支查找结果，该 Session 的下一个面板从它们开始，除非 Session 换到了其他目录。它不重复已确认就绪的托管平台的登录检查，也不重复已显示变更请求的 Session 的分支查找；状态读取被以未登录拒绝时会触发一次登录检查。

**Host 保留已审阅标记。** Host 按 head 提交保留为变更请求读到的已审阅标记，受与所保留评审讨论相同的限制。保存一个标记会替换所保留的对应文件状态，并保留评审讨论，所以一次保存只需要提供方的那次写入，不再读取。

## Alternatives considered

**只限制快照查询的大小**能让每个查询足够短，但 61 个 pull request 的列表仍需要 8 个查询和 38 s，而读回的字段列表根本不显示。

**调大 `fetchTimeoutMs` 或并发发送快照查询**不改变 GitHub 处理每个查询的时间，而且 GitHub 只允许一个账号每 60 s 使用 60 s 的 GraphQL CPU 时间。

**带条件请求的 REST** 经 `gh` 返回 HTTP 304 时不消耗速率配额，但每个 pull request 要启动一个 `gh` 进程，各约 1.2 s，而且没有检查汇总状态。

**Webhook** 需要一个接收它的服务端；Host 是本地进程，通过用户自己的 `gh` 读取。

**给 `watch` 加 `level` 选项**会让一个方法有两种监听方类型；分成两个方法，每种监听方的更新类型都是确定的。

**存储读取时间**只有在 Host 重启恰好落在一个轮询间隔之内时，才能省下重启后的第一次简报读取，代价是改动已存记录。

**每个主机一个队列、用户操作单独一条通道**能让刷新越过正在进行的读取。两个层级已经把打开的面板和列表分开，一个快照查询耗时 2 至 6 s，所以这个队列在一次刷新上最多省下这么多时间，代价是第二套调度。

**给每个间隔加随机偏移**会把请求在时间上摊开，这和实测的开销所需要的正相反：它会把一个查询本可以一起读的变更请求分开。

**读取被拒绝后暂停整个主机**省不下多少：14 个全部被以未登录拒绝的变更请求一起退避，一小时只花 10 个查询。

**每个间隔只发一个后台查询的预算**只在超出一次读取能及时读完的规模时才有意义；100 个 pull request 用了两个各 50 个的简报查询，共 7.6 s。

**推送之后用更快的节奏**（一个同类产品用 5 秒、持续一分钟）需要再加两个配置项；按活跃间隔，看到新检查最多晚约 10 秒。

## Consequences

在实测的场景里（绑定了 14 个打开、17 个已合并的 pull request），列表的一次轮询是一个约 1.7 s 的请求，取代原来包含 31 个快照、被 GitHub 以 HTTP 504 拒绝的查询，已合并的不再读取。按 60 秒的空闲间隔，页面可见时每小时 59 个查询，隐藏时没有。等待已过半的变更请求会随它所在通道的任何一次读取一起读，所以相邻的变更请求有检查在运行时，它被读取的频率最高是自身间隔的两倍；查询个数不会因此增加。简报报告 GitHub 的检查汇总状态，检查列表完整的快照则根据每个检查的最新一次运行自行得出结果；实测的 61 个打开的 pull request 两者全部一致，不一致时没有机制去对齐。一个快照查询和它的 pull request 的续页共用一个时限，所以评审讨论很多的 pull request 可能让它所在查询的最多 8 个 pull request 一起失败。在代码托管平台上直接改动的已审阅标记，要等到 `reviewRefreshMs` 之后或读者刷新时才显示。一直可见但没有人看的页面会继续轮询。
