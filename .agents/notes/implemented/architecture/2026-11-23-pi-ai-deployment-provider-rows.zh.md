# Agent Note：以提供方条目承载部署方下发的 pi-ai 提供方

Status: implemented

[English](2026-11-23-pi-ai-deployment-provider-rows.md) | 中文

## 问题

所有 pi-ai 提供方路由都位于同一个字段：`llm-pi-ai` 条目配置中的 `providers` 字典。设置条目 `config` 的 patch 会替换此前各层的整个配置。Models 页把用户的提供方保存为 profile patch 中对该条目的覆盖；为一台机器上每个 profile 下发提供方的部署方则写入 home patch，而 home patch 在 profile patch 之后应用。两者因此在两个层里写同一个字段，造成两个结果：

- home patch 的字典替换用户的字典，用户的提供方不再提供服务。
- 配置编辑器拒绝此后对该条目的每一次保存，因为组合出的配置与它将要保存的内容不同（`Configuration for "llm-pi-ai" is overridden by a home patch or command-line overlay`）。

`--patch` overlay 以及任何在 profile patch 之后添加提供方的层同样如此。

## 决策

添加提供方的层写一个独立的条目，字典保持不变。

- [`@deepseek-ai/dsh-llm-pi-ai/provider`](../../../../packages/llm/llm-pi-ai/src/provider-row.ts) 是适配器包的第二个插件。它的配置是 `provider` 中的路由键，以及与之并列的字典条目的各 profile 字段；这些字段由同一组字段 schema 构建，每个字段都可实时生效。
- 该条目通过适配器条目提供的 [`ctx.piAiProviders`](../../../../packages/llm/llm-pi-ai/src/registry.ts) 注册自己的路由。适配器把已注册的路由与字典的路由一并提供。
- 多处声明同一条路由时，组合后条目列表中位置最靠后的那处生效。字典按适配器条目所在的位置计，因此 home patch 或 overlay 添加的条目会替换字典中同一路由的条目，该条目离开后字典条目重新提供服务。这与 patch 既有的优先级一致：由靠后的层决定。
- 可配置提供方目录对条目所服务的路由以该条目寻址（`settingsNs` 为条目 id，`settingsPath` 为空），其余路由以字典条目寻址。
- Settings 和配置编辑器没有变化。[Models 页](../../../../packages/client/ui-settings-models/src/client/store.ts)凭 settings 已经发送的内容识别提供方条目：条目的表单声明的字段与字典条目表单的字段相同，因为两者由同一组字段 schema 构建。页面保留对字典的读写，把条目所服务的路由与字典的路由并列列出且不提供删除，并在条目 namespace 的根部以 pi-ai 卡片打开它。输入的密钥保存在条目指名的凭据引用下；修改后的字段交给配置编辑器，它拒绝由 home patch 或 overlay 添加的条目。

字典、已保存的 profile patch 以及页面对字典的写入都没有变化，因此不需要转换任何已保存的配置，也没有接口被移除。

## 考虑过的替代方案

- **每个提供方都是条目，不再保留字典。** 这样每一层只添加、修改或移除一条路由，用户的提供方与部署方的提供方是对称的。但它移除了已发布版本的 profile patch 所保存的字典，因此需要在启动时转换每个已保存的 profile、对启动器不拥有的文件给出拒绝、编写升级指南、提供供设置页添加和移除插件条目的通用操作，并让 Models 页以条目起草。它的一个实现在启动器、配置编辑器、settings、其 Remote 控制器和页面上共新增约 5,500 行（含测试与文档）。上述问题不需要这些：只需让当前覆盖字典的那一层不再写它。
- **跨 patch 层深度合并 `config`，或增加按路径寻址的 patch 操作。** 前者改变每个插件每个 patch 的含义，后者增加一种所有层都要理解的 patch 形式，而目的只是服务一个字典。在适配器里增加第二个提供方来源，只影响拥有该字典的包。
- **为部署方再挂一个 `llm-pi-ai` 条目。** 每个组合中适配器只提供一份目录和一次模型发现注册；第二个条目会以 `DUPLICATE_DIRECTORY` 启动失败。
- **在 patch 文件之外为部署方提供方设置专用文件。** 这会增加一个 Loader、热重载和配置编辑器都不认识的配置来源。
- **让同一条路由的两处声明同时提供服务，以显示名称区分。** 请求、Session 记录和默认模型设置都以路由键指名，pi-ai 也按它分派，因此一个键只选择一份 profile。部署方若要在用户自己的同厂商提供方旁边提供另一个提供方，应给条目使用另一个路由键并设置 `displayName`。自动重命名冲突的键被否决：这个键会随另一层的出现或离开而变化，而已保存的 Session 和默认模型都指向它。
- **在 Models 页标出部署方的提供方。** 为由后续层决定的条目显示标签和只读卡片，需要配置编辑器报告每个条目由哪一层决定，并由 settings 及其 Remote 控制器把它传给页面。配置编辑器本来就拒绝这类写入，因此这些包保持原样，卡片显示这次拒绝。设置页能否编辑由 home patch 决定的条目，是配置编辑器的问题，与本适配器无关。
- **用一个新字段告诉页面哪些条目是提供方条目。** 在 `dsh-llm` 的目录条目上加字段，或由 settings 转发每个 namespace 的插件名，都可以指明条目的适配器。settings 已经发送的表单足以识别该条目，因此没有接口承载它。

## 影响

- `providers` 字典无法启动时适配器条目失败，各提供方条目等待该条目提供的服务，因此字典修复前没有任何 pi-ai 路由可用。无法启动的提供方条目只让自身失败。
- 路由键不对应任何已安装 pi-ai 提供方的条目不继承目录：它需要声明 `api`、`baseURL` 和 `models`。
- 字典条目位于同一路由的条目之后时不提供任何服务，在该条目运行期间 Models 页也不显示它。
- 除了没有删除控件之外，Models 页上没有任何内容把部署方的提供方与用户自己的区分开；修改由 home patch 或 overlay 添加的条目的字段，要到保存时才被拒绝。
- 页面把表单恰好声明 pi-ai profile 各字段的任何 namespace 都视为提供方条目。
- 重新组合的配置可以在不重启条目的情况下移动条目。注册表在 `app-boot/config-reload` 时重新判定生效的条目；以其他方式调整条目顺序的组合，在有条目注册、变更或撤回之前保持原先的顺序。
- 覆盖 `llm-pi-ai` 条目配置的 home patch 会替换已保存的字典，配置编辑器拒绝对该条目的保存。
