# Agent Note: Compose tool registries under a scoped root

Status: implemented

English | [中文](2026-11-19-composable-tool-registries.zh.md)

## Problem

`ctx.tools` held scoped tool definitions, and a separate `ToolExecutor` selected by `setExecutor()` decided how the model reached them: the native executor declared each visible definition, and the PTC executor declared `run_code` plus a generated SDK. A second program entry could not reuse that composition. CUA built `cua_run_code` with `createRunCodeTool()`, a factory that copied a fixed definition list into private bindings, so the PTC executor and the CUA program tool each owned a different binding source. Program styles that differ in entry names, helpers, or output, such as Pi and Codex code mode, would each need another factory or executor.

Tools whose availability depends on Agent state used `register(tool, { when })`. Before every step the loop awaited every condition through `resolve()`, and the resulting `ResolvedToolSet` had to reach prompt assembly, the batch, and every PTC subcall. Each consumer of the registry therefore accepted a step set, and conditions ran for every Agent and step even when the state they read had not changed. Prompt sections hid their guidance by asking `ctx.tools.get()` whether their tool was visible, so the registry answered which tools a scope had separately from what its model could call.

## Decision

A `ToolRegistry` is a set of directly callable entries with `register()`, `include()`, `get()`, and `getAll()`. `include(registry)` reads another registry's entries at every query, so the source keeps ownership and later changes appear without republishing. A registry owns no batch execution: `ctx.tools.execute()` runs every batch.

Each scope selects one root registry with `setRoot()`, and `ctx.tools` routes to it. A tool registered or included in a scope reaches the root that scope selects and the roots selected below it: `setRoot()` makes the root include a private view of the registrations, which resolves each viewing scope's tools with nearest-scope shadowing and that scope's restrictions; a root that includes or reads `ctx.tools` fails with `ToolCompositionError` when it is selected or in the later lookup or batch that reaches the read; `setRoot()` includes the view only once in a root selected again and emits `tools/change` when a root is selected or unloads. Inclusions in an ancestor scope count as inherited, so a child's `restrict()` applies to them; two different definitions offered by the deciding scope fail as `INVALID_TOOL_COMPOSITION` when they register. `ctx.tools.get()` and `getAll()` return the selected root's entries, and `ctx.tools.execute()` resolves each call through the root selected when the batch starts; without an available root all three throw `ToolRegistryUnavailableError`. `NativeToolRegistry` offers every registration a scope sees as an entry. `PtcToolRegistry` offers one program entry and binds the registrations in programs, so under a PTC root `getAll()` is `[run_code]`. CUA includes a private `PtcToolRegistry` named `cua_run_code` whose only binding is `cua`, so the PTC root and the CUA tool share one implementation.

A tool section that is shown only while its tool is available travels with the definition as `guidance`, as the filesystem, search, `apply_patch`, schedule, on-demand MCP catalog, and delegation sections do: `ctx.tools.register()` registers the section in the same effect as the tool and renders it only while the viewing scope's registrations resolve that exact definition, which covers native declarations, PTC program bindings, restrictions, and nearer same-name definitions without a registry query. Tools that share guidance name one `section` and declare the same guidance, which the system prompt renders once with the names of the tools the viewing scope resolves; the delegation tools share `tool:subagent` this way. Other tool sections, such as bash's, are registered apart from their tool and stay while their plugin is loaded. Guidance may mention another plugin's tool without checking for it. New guidance is discouraged: what the model needs to know about a tool belongs in its description and parameter descriptions, which every root delivers with the tool, while a section costs prompt space in every step and is a second place to keep in sync. `guidance` exists so that the prompt text of tools that predate this rule stays byte-identical. A per-Agent provider registers its tools in an `AgentToolRegistry`, which `ctx.tools` does not see one tool at a time, so it decides a section's text for each Agent from its own registry.

One question has no answer in the root view: which of several Timeline installations is nearest to an Agent. `dsh-timeline` asks with the scope-filtered package event `timeline/installation`, which each installation answers with its own record; the asker dispatches through the Agent's carrier and takes the nearest record in the scope chain. The listeners belong to each instance's context, so unloading withdraws them, separate applications never see each other's instances, and copies of one package in a composition answer alike.

Providers own per-Agent availability. An `AgentToolRegistry` included in `ctx.tools` shows each Agent the tools its provider added for it with `set(agent, names)`, and its unscoped view lists every registered tool, so restrictions, `toolOrder`, and catalogs can name a tool before an Agent sees it. A call without an Agent resolves that view and reaches the tool's body, which checks `exec.agent` when it needs one; Plan, Office, Team, and Web tools reject such calls. Providers call `set()` when their state changes: on Agent creation, on the provider's own state changes, on `agent-preset/selected` when a blank Session's preset change moves a live Agent into the provider's preset, and in a load-time pass over existing Agents. Web availability depends on the Agent's model route and credentials, so the Web tools also check again on `model/selection`, on a `request/header` naming another provider, on credential changes, and on `web/providers-changed`.

AgentLoop captures `ctx.tools.getAll(agent)` as a `ToolStep` before it assembles each step. The prompt declares exactly those entries, and the step's batch and program calls execute only the same definitions; a PTC registry also pins the bindings it declared for the step. A replacement or addition while the model responds takes effect in the next step; a removal or a provider's withdrawal for the Agent applies at once, so the step's unstarted calls to that tool fail as `UNKNOWN_TOOL`. A model-direct call to a tool the root binds only in programs fails before `tools/pre-execute`, approval, guards, and execution wrappers, and its message names the entries the step can call, so the model is pointed to the program entry. Dispatch runs exactly the definition captured when the call was prepared, and fails as `UNKNOWN_TOOL` when the root no longer offers it.

## Alternatives considered

**Keep `ToolExecutor` and add a factory per program style.** Every factory would copy definitions into private bindings, as `createRunCodeTool()` did, so restrictions, scoped shadowing, and live registration changes would need reimplementing per style. A registry that includes the registrations reuses them.

**Keep `ctx.tools` as the store whose `get()` lists what a scope has, and let each root include `ctx.tools`.** Lookups then answer a different question than the model's tool list: under a PTC root `ctx.tools.get('read')` finds a tool the model cannot call, step capture needs a separate hidden query for the root's entries, and every root reads `ctx.tools` back through a cycle guard. Routing to the root gives one answer, the entries the root offers.

**Copy each registration into every root.** Each root implementation would need a scoped store with shadowing and restrictions, a scope parameter on `register()`, and a replay of every registration when a root loads, reloads, or changes with a preset switch. The private registrations view gives the same routing with one store.

**Gate guidance on tool presence.** Each section would ask the registry whether its tool is visible, which under a PTC root must count program bindings, so the registry would answer a second question for every plugin. `guidance` makes the same decision inside `ctx.tools`, from the registration it already holds.

**Make the restricting plugin hide the guidance.** A plugin that calls `restrict()` would register an empty same-name section for the restricted scope. It would need to know which section belongs to which tool, including the shared `tool:subagent` section, and every new restriction site would repeat that work.

**Keep step-time `when` conditions.** Conditions made every consumer accept a step set and evaluated every condition for every step. Providers already know when their state changes.

**Emit an awaited event before each step captures its tools.** The Web route check could then read the step's exact model selection, and Plan and Team could reconcile from the log on every step. That kept a per-step extension point in the agent loop for one consumer, and it ran every listener for every Agent and step although the inputs change rarely; most inputs change through an event, and the inputs without one are listed under Consequences. The Web tools instead check again when the route, a credential, or the providers change; a step that starts while a check runs uses the previous answer.

**Register a per-Agent tool directly in `agent.ctx`.** The registration would belong to the Agent's own scope, which `restrict()` does not filter, so a child's `toolFilter` could no longer hide it. An included `AgentToolRegistry` keeps the tool inherited.

**Store a binding table per PTC registry instead of including the registrations.** The table would need its own update path for every registration, restriction, and preset change, and it could diverge from what native roots offer.

## Consequences

One registry interface serves the native root, the PTC root, and program tools such as `cua_run_code`, so new program styles are registries rather than executors, and a custom root implements four methods. Tool lookups take no step argument, and only the agent loop and registries handle `ToolStep`. Execution records carry the definition each call resolved, so policies read it instead of looking a name up again. Code that reads `ctx.tools` needs a selected root, including tests, and an Agent under a PTC root sees only `run_code` there: Cordis Inspect, the Claude Code mods `$.tool.list`, and the Cordis host sandbox's `ctx.tools.schemas()` and `get()` list only the program entry and throw `ToolRegistryUnavailableError` without a root; a LiveShare viewer fork whose deployment root offers no `read` is refused as `tool-unavailable`; and a blocked browser MCP client's inherited tools stay bound although their calls are still refused. `restrict({ deny })` accepts a name nothing offers yet, so Timeline denies `todo_write` for every Agent it manages.

A restricted tool's `guidance` stops rendering for the restricted scope. Other tool prompt text stays when its tool is restricted ([limitations](../../../../packages/core/tools/README.md#known-limitations-and-deferred-work)): sections registered apart from their tool, such as bash's; the sections of per-Agent providers (Web, Plan, Office, Team) and CUA; the delegation depth context; the `send_message` and `list_agents` lines of the subagent identity context; and the skill catalog message. A retirement is detected only for a source this process saw, so a Session resumed in a process without that source, for example without the MCP loader or a delegation tool, keeps the guidance it saw without a notice ([source lifecycle](../../../../packages/core/system-prompt/README.md#known-limitations-and-deferred-work)). Providers of per-Agent tools must initialize Agents that exist when they load, and they restore a resumed or forked Session's state from its log. A provider that misses a state change leaves the tool stale until its next update, which a step-time condition would have corrected. Readiness inputs without a change event apply at the Agent's next check: edited Web provider settings, and the route of a blank Web Session that follows the default model, which changes when another Session saves a new default. That Session's first step uses the answer checked for the old route; the step's own `request/header` starts a check, and if the new route is not ready the tool is withdrawn while the model answers, so a declared `web_search` call fails as `UNKNOWN_TOOL`, or with `WEB_PROVIDER_CREDENTIAL_MISSING` when it starts before the check settles. A tool withdrawn while the model responds fails that step's calls as `UNKNOWN_TOOL`, where a step-time condition kept it for the step and left its body to report the current state, for example `TEAM_DISABLED`. Plugins that called `setExecutor()`, `resolve()`, `schemas()`, or `register(tool, { when })`, roots that implemented `execute()`, and code that read registered tools through `ctx.tools.get()` migrate through the [upgrade guide](../../../../docs/upgrade-guide/v0.2.3-alpha.2/tool-registry-roots/guide.md).

[registry-composition.spec.ts](../../../../packages/core/tools/tests/registry-composition.spec.ts) covers root selection, routing to roots that load later, unavailable roots, live inclusion, inherited restrictions, ambiguity, inclusion cycles, per-Agent tools, and step admission, and [guidance.spec.ts](../../../../packages/core/tools/tests/guidance.spec.ts) covers guidance under restrictions, shadowing, shared sections, and retirement. Provider tests cover each per-Agent trigger, including providers loaded after their Agents.
