# Agent Note: 源码构建的 CUA helper 使用开发签名身份

Status: implemented

[English](2026-10-29-cua-dev-signing-identity.md) | 中文

## 问题

源码检出用临时签名编译 `DSH Computer Use.app`。macOS 按 Bundle ID 和被授权代码的指定要求保存辅助功能与屏幕录制授权，临时签名的指定要求就是代码哈希。因此每次构建内容变化、每换一个 worktree，都需要重新授权；这些构建还与正式 helper 共用 Bundle ID，会替换正式版的授权条目。

## 决策

Host 以开发版构建源码检出，Bundle ID 为 `com.deepseek.harness.computer-use.dev`，名称为 `DSH Computer Use Dev`。正式版及其打包流程不变。按[共享 helper 决策](2026-10-09-cua-shared-native-helper.zh.md)的要求，授权仍归经 LaunchServices 启动的 helper 应用。

`sourceSigning` 默认为 `ad-hoc`，不读取已有身份或修改钥匙串。显式选择 `local-identity` 后，构建自动初始化或复用本机身份。初始化在专用钥匙串中创建自签名代码签名证书，把随机钥匙串密码保存在旁边仅所有者可读的文件中，通过密钥分区列表允许 `codesign` 使用私钥，并把该钥匙串加入用户钥匙串搜索列表。`codesign` 只从这个列表查找签名身份。固定身份构建每次签名前都用保存的密码解锁钥匙串，避免密码或密钥访问窗口。跨进程文件锁串行化不同 worktree 的初始化和移除，防止并发创建不同证书。签名得到的指定要求只包含 Bundle ID 和证书，同一台机器上签出的所有构建都相同，与代码哈希和路径无关。

即使不使用时间戳服务器，证书签名也会写入签名时间。开发版发布时记录每个未签名应用与签名身份对应的目录，再次构建时直接选中该目录，不重新签名，因此相同源码保持同一个可执行文件摘要和同一个共享服务。缓存使用证书指纹；显式证书名称可能对应续期后的证书，因此不复用缓存。签名初始化失败会中止构建；异常信息不包含密码或完整命令参数。显式传入 `--identity` 时覆盖配置的签名方式。

## 考虑过的替代方案

**把权限交给启动终端。** 直接启动服务时，macOS 把权限归属到启动 DSH 的终端或编辑器。该应用运行的所有程序，包括模型执行的命令，都会带上这些权限。

**默认固定签名。** 固定身份可以保持签名要求，但会保存私钥并修改钥匙串搜索列表。默认临时签名让用户自行选择是否接受这些改动，代价是二进制变化后可能需要重新授权。

**把自签名身份放进登录钥匙串。** 登录钥匙串已解锁且在搜索列表中，但要让 `codesign` 不弹窗地使用其中的新私钥，需要用户的登录密码。

**只在签名期间把钥匙串加入搜索列表。** 正式打包脚本对单次调用这样处理。多个 worktree 并发构建时会互相覆盖读取和恢复的列表，构建被中断时条目也会残留。

**用固定的启动器运行各 worktree 的 helper。** 授权会跟随启动器，但任何本机进程都能让它带着这些授权运行任意可执行文件，暴露面与保存的私钥相同，还少了签名检查。

## 后果

启用固定签名的检出和重新编译共用签名要求。真实授权在重新编译和跨 worktree 后是否保留，仍需手动验证。该用户的任何进程都能读取钥匙串密码，并签出获得开发版授权的代码；正式 helper 的授权不受影响，而且同一用户本来就能修改下一次构建会签名的 Swift 源码。初始化会改变用户钥匙串搜索列表，直到运行移除命令。移除前需切回 `ad-hoc`，否则下次构建会重新创建身份；切换签名方式或更换身份可能需要重新授权。系统设置中已有的授权在移除后仍然保留。原有的临时签名源码授权不会沿用，开发者需要给 `DSH Computer Use Dev` 授权一次。`dev_signing_e2e.py` 检查两个不同构建共用同一个指定要求，并确认移除后搜索列表已恢复。
