# Agent Note: Team 任务通知普通 subagent 收件箱

Status: implemented

[English](2026-10-19-team-task-board-inbox.md) | 中文

## 问题

subagent（子智能体）树已经提供 agent 身份、发现、路由和生命周期。第二套 Team 名册会从过期历史记录授予分配权限，并重复普通成员 UI。Team 所有的等待会观察无关状态变化，却错过调用者已有的待处理输入。等待前要求其他成员活跃，也混淆了轮次活动与有用输入是否可能到达。

## 决策

subagent 树就是 Team。普通 subagent 控制工具负责身份、通信、发现、中断和 `wait_agent`，独立于可选任务板。必需运行时上下文说明当前身份；共享策略解释消息接纳、结果收集、等待和共享文件协调。现有运行时上下文机制记录并保留此身份，无需修改 loop。

`wait_agent` 先订阅，再检查当前调用者的下一步收件箱。已有待处理输入时立即返回；后续输入结束等待。排队的下一轮输入、其他收件箱和单纯状态变化不会结束等待。等待既不消费输入，也不启动 agent。超时、取消、调用者释放和插件卸载会结束等待并移除其资源。

Team 负责任务存储、比较并交换命令、依赖和任务策略。根可将任务分配给自身或 subagent 服务发现的任意可达的可继续执行后代。历史名册记录不授予权限。浏览器 Team 面板显示任务；普通 subagent 导航负责成员列表。

任务追加并刷盘成功后，Team 向其他每个本地在线成员的下一步收件箱接纳紧凑通知。同一任务板的待处理通知通过替换合并，保留现有收件箱 id。通知绝不恢复冷成员或启动空闲轮次。接收者行动前读取当前任务。尝试所有接收者后，投递失败会报告已提交任务修订和失败接收者；调用者不能将其视为提交失败或盲目重试创建。

历史名册、邮箱和任务代次保持可读，绝不重写。已接纳通知使用普通收件箱持久化。这部分取代 [Agent Teams](../feature/2026-08-05-agent-teams.zh.md) 和 [subagent 队友](2026-10-15-agent-teams-as-subagents.zh.md)中的名册和等待决策；它们的任务持久性和单一 agent 身份理由仍有效。[必需运行时身份](2026-10-13-team-identity-runtime-context.zh.md)仍是保留机制的决策依据。

## 考虑过的替代方案

**保留独立 Team 成员关系和等待。** 这在树和收件箱之外引入第二套权限来源和观察机制，允许历史名册行和无关活动影响当前工作。

**轮询任务板或等待 Agent 状态。** 两者都不能标识调用者可处理的输入。提交后通知让一个普通收件箱等待同时服务消息、完成、引导和任务变更。

**自动唤醒每个任务所有者。** 任务就绪并不构成启动轮次的指令。不唤醒通知保留显式继续执行，并避免为后台任务板更新进行冷恢复。

**将通知失败报告为修改失败。** 任务已经持久化。隐藏这一事实可能导致重复创建或过期重试；已提交修订和失败接收者保留了恢复所需信息。

## 后果

任务完成、收件箱可用性、Agent 活动和 Agent 生命周期保持独立。空闲成员保留通知直到继续执行；冷成员下次运行时发现当前任务。合并有意省略中间通知，而任务日志保留每个已提交修订。

验证覆盖待处理输入和订阅竞态、接收者精确隔离、下一轮排除、等待清理、任意深度分配、历史记录无权限、合并、不唤醒投递，以及已提交状态错误报告。录制的 subagent 和 Team 工作流覆盖模型指导和通知。
