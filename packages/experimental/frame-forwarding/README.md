# @deepseek-ai/dsh-frame-forwarding

English | [中文](README.zh.md)

## Summary

A Host plugin that renders in its own native process can show those frames in the Desktop document without copying pixels. The `frameForwarding` Host service opens single-producer channels with transferable producer credentials, enforces frame and byte budgets, and has Desktop present accepted textures; the `frameForwarding` Client service connects the renderer to a channel and lends each frame to the consumer's drawing callback. The LibreOffice Kit is the first producer.

<a id="use-this-package"></a>
## Use this package

Desktop preinstalls the frame receiver on macOS and Windows. Both the bundled preview and a frame-forwarding plugin installed through Plugin Manager use the receiver supplied by the running Desktop.

Insert the package beside the consumer plugin as the row `frame-forwarding` without a config. Every consumer bundle inserts that same row, and the Loader keeps one row per id, so consumers enabled together share one instance: disabling one consumer leaves frame forwarding and the other consumers' channels running. Tune its limits with a patch targeting `frame-forwarding`, which applies after every bundle. Consumers share the window's byte budget. In the Host, read the service with `ctx.get('frameForwarding')`, probe `capabilities()`, then call `channel()` for `{ tx, rx }`. Hand `tx` to the producer process, for example as the credential a child process receives from its parent; any process holding a copy may connect, nothing binds a PID, and `tx` never goes to the renderer, a log, or a diagnostic. Send `rx` to the renderer. Each channel serves at most one producer connection: a second candidate is refused as `channel-busy` while one is connected, and once the producer disconnects or exits the channel closes permanently (`closed` after a normal disconnect, `failed` after a transport or protocol error). `isOpen(rx)` reports whether the channel is still open, and `close(rx)` closes it permanently. A channel also closes when the Cordis scope that read the service with `ctx.get` is disposed, for example when its plugin reloads; a Remote method's `this.ctx` is the Remote gateway's scope, so a consumer that opens channels during Remote calls closes them in its own disposal. A channel closes as `lost` when Desktop can no longer account for a frame it presented, for example after Chromium's GPU process exits; its owner probes `capabilities()` again and opens a channel in its place. `capabilities()` reports `gpu-compositing-disabled` once Chromium composites in software, for example after repeated GPU process crashes. A Host that cannot present frames, such as any Host outside Desktop, reports `supported: false` with a reason, and `channel()` rejects; reasons are diagnostics from an open set, so consumers branch only on `supported`.

In the Client, read `ctx.get('frameForwarding')`, which exists only in a document that displays the Host's frames, the Desktop document, so consumers test for the service rather than for Desktop, and `connect(rx)` to obtain a `FrameRx` for that channel. `setViewport` sends a strictly increasing viewport version; if submitted while the channel is still idle, the Host retains it and applies it once the producer connects before delivering its frames. The Host delivers the producer's frames whose generation does not exceed the channel's latest viewport version, including earlier generations still in flight, and none while that viewport is invisible; outside a document mount, the receive channel releases frames of other versions unseen. A receive channel connected again, for example after a renderer reload, starts counting below the version the Host kept: `mount()` retries above it, while `setViewport` rejects with an error that names it. A viewport sent before the producer connects resolves and is applied once it connects. A viewport the producer refuses or does not acknowledge within `requestTimeoutMs` rejects with that error and leaves the channel open; the next viewport is still sent. `ready(signal)` resolves with the connection ID once the producer acknowledged the latest viewport. `closed` settles once with why the receive channel stopped routing: `closed` after its owner, a normal producer disconnect, or `close()` closed it, `lost`, or `failed`. A receive channel has one consumer kind at a time:

- **Mounted video.** Call `mount(element, failure, options?)` on a sized container to feed received frames to a video element through `MediaStreamTrackGenerator`. `options.visible` sets the initial explicit visibility (default `true`), and `setVisible(visible)` updates it while mounted. When a new mount reuses an open channel, it advances past the viewport version the Host retained. Call the returned disposer to detach the video and stop its track. Unmounting a visible view queues an invisible viewport so the producer can trim idle surfaces.
- **Continuous stream.** `consume(present, failure)` presents frames newest first. While `present` runs, only the newest arrived frame waits; a newer arrival releases the waiting one unpresented. `failure` receives the connected producer's errors, the channel's closure, or an error `present` raised, and the stream stays subscribed.

`onEvent(listener)` reports channel state, viewport, errors, and content submissions. Each successful video track write emits its generation, including repaints of the same generation. Consecutive content clears emit once. New listeners receive only the latest submitted generation. It cannot confirm when Chromium displays those pixels.

The mount reports its physical size, device pixel ratio, and visibility (combining explicit `visible`, DOM connection, intersection, non-zero size, and `document.visibilityState`) to the producer, coalescing viewport changes. A hidden document sends an invisible viewport immediately.

While mounted, `setContentView({ x, y, scale })` sets the content coordinate at the element’s top-left corner and CSS pixels per content unit; `undefined` restores fill mode. `setContentWindow({ x, y, width, height })` binds a window to a new viewport version and resolves with the acknowledged viewport to use as paint generation; an unchanged window returns the current acknowledgement without incrementing. Call it only after the previous paint resolves, then request the next paint after this promise resolves. Frame forwarding serializes viewport updates, not paints: a mount update already in flight completes first, and unsent window requests coalesce to the latest window. Numeric validation synchronously throws `TypeError` without sending messages for non-finite values, coordinates beyond ±2²⁴, non-positive extents or extents above 2²⁴, or scale outside (0, 64]. Both setters throw outside a mount; pending window requests reject with `cancelled` when the display unmounts.

`FrameRx.submittedWindow` reports the last content window written to the mounted track, including after a newer viewport request. It is undefined before submission, in fill mode, and after unmount. The video positions each submitted frame using its generation’s content window and the latest view. During resizing, document images retain their aspect ratio while the next frame is pending. Frames fill the mount in the absence of content mapping. Returning to a detached tab resumes its existing video track.

Each consumer callback receives a `FrameForwardingFrame`, `{ image, metadata }`, lent until the callback returns or its promise settles; frame forwarding then closes `image`, which returns its resources to the Host. Draw, upload, or copy `image` during that period. A Desktop shared texture returns to the producer only after Desktop reports every Electron reference gone, which Electron reports after GPU work that used the image completes ([`getVideoFrame`](https://www.electronjs.org/docs/latest/api/structures/shared-texture-imported)). A retained `image` or clone keeps its resources in use until it closes. How `image` is backed and its pixel `format` depend on the Host, so read pixels only through `drawImage`, or through `copyTo` with an explicit `format`. Consumers pass no queue sizes and release no frames; `close()` stops consumption and completes after every lent frame is released. Frame metadata carries `rx`, `connectionId`, `requestId`, `frameId`, `generation`, `revision`, `width`, and `height`; `generation` is the viewport version, and the consumer chooses `requestId` and the producer echoes it.

Config, read by the Host plugin only: `maxFrames` (frames per channel that the producer, Host, Desktop, and renderer hold together, default 3, 3–16), `maxBytes` (allocation budget that every channel of the window shares: `auto`, the default, is half of physical memory and at least 256 MiB; the budget never exceeds physical memory, and a larger byte count is reduced to it with a Host warning when the first channel opens), `requestTimeoutMs` (adapter detection, frame delivery including each Desktop shared-texture exchange, producer handshakes, and producer acknowledgements; a frame's presentation through Desktop waits at most 30000 ms, Desktop's limit), `maxPendingRequests` (control requests per connection awaiting acknowledgement), and `maxQueuedEvents` (channel events retained for a renderer that has not read them; a newer state of a channel replaces its queued one, and beyond the limit the unread events become one snapshot of every channel's state, including the newest `maxQueuedEvents` unread closures of channels already torn down, and dropping unread frame errors and older closures). A stream producer that keeps one of its `maxFrames` surfaces out of flight always has a render target, so its state advances without waiting for credit and its newest complete frame goes out when a surface returns.

The plugin reads the absolute addon path from Desktop Host, checks the build record for the platform, protocol version and handshake capabilities it requires, then loads the receiver on first use. For development builds run `pnpm --dir apps/desktop run build:native`.

The native producer interface is internal. The [design decision](../../../.agents/notes/implemented/architecture/2026-10-15-desktop-shared-texture-api.md#native-producer-sdk) explains why SDK publication is deferred.

**Stability.** The package is experimental: breaking changes to its Host and Client services follow its semver. Its package name carries no `experimental` prefix, so bundle patches and profiles that name it keep their reference when it leaves the experimental group; the experimental classification still governs its dependency isolation and promotion. The wire protocol is at version 2, and a receiver refuses a producer of another version; within a version it changes only by adding handshake capabilities that both sides check, so a receiver refuses a producer without a capability it requires, and a producer refuses a receiver that does not acknowledge one the producer relies on.

<a id="security-semantics"></a>
## Security semantics

Frame forwarding is the only native-rendering API plugins use; these are its guarantees.

- **Who can open channels.** Any Host plugin can read `frameForwarding`. A channel grants authority only to holders of its `tx`; the plugin decides which processes receive it, and copying it revokes nothing.
- **Producer authentication.** `channel()` returns a credential with a 256-bit random secret and an unguessable endpoint name: a Mach service on macOS, and on Windows a named pipe that admits only the receiver's user and rejects remote clients. The producer's `hello` must carry the secret, protocol version 2, and the `transferable-tx` and `producer-local-handles` capabilities; the receiver compares the secret in constant time, refuses a mismatch as `invalid-credential`, another version as `protocol-mismatch`, and a producer without a capability as `transferable-tx-required` or `producer-local-handles-required`, and closes only that candidate. Each physical connection checks that every later packet comes from the kernel-reported sender of its handshake (Mach audit trailer, `GetNamedPipeClientProcessId`) and carries its connection ID; that PID grants no authority. `close(rx)` withdraws the endpoint, so the credential stops connecting.
- **Producer handles.** A producer names only objects it owns. On Windows each frame carries a handle value in the producer's process, and the receiver duplicates it from that process with the access it opened when the producer connected; a value that names no handle of a live producer ends that connection without touching any Host handle. ready echoes the capabilities the receiver accepted, so a producer refuses a receiver that would read its values as Host handles. macOS transfers Mach port rights, which the kernel names in the receiver.
- **Producer isolation.** Each channel serves at most one producer connection and never preempts it. Disconnecting the producer closes the channel permanently, so frames and credit belong exclusively to that connection; owners open a new channel for a replacement producer.
- **Resource bounds.** Each channel holds at most `maxFrames` surfaces in flight, including the frames its renderer holds; all channels share one `maxBytes` allocation budget, and each connection queues at most `maxPendingRequests` control requests. A producer whose allocation does not fit the remaining budget waits until other channels return surfaces; its channel stays open, so its consumer keeps what it shows and draws a placeholder where content has not arrived. Handshakes and acknowledgement waits end at `requestTimeoutMs`. A producer whose view is hidden or covered returns its idle surfaces to the shared budget: the Kit engine trims after acknowledging an invisible viewport. The producer's credit for a frame returns only after Desktop reports all Electron references to its texture gone; an `invalidated` settlement queues its notice, then stops the receiver and the frame's connection before releasing the frame, so the producer never regains that texture's credit; the forwarder closes the channel as `lost` when it handles the notice.
- **Renderer input.** Frame metadata is producer-supplied; the Client validates it and releases any texture without valid metadata or without a connected receive channel. The Host validates every renderer viewport and rejects a version that does not exceed the channel's current one. A frame of a generation the renderer never sent is released unseen, whatever the producer acknowledges.
- **What plugins do not see.** Plugins do not get Mach ports, Win32 handle transfer, Electron, or Desktop's internal texture interfaces, which are not supported for plugins. The Host plugin holds the only claim on the Desktop Host's `sharedTexture` service from load to unload, and the Client plugin consumes the Client `sharedTexture` service from its start to its disposal, so another consumer of either fails at once. When another consumer took the `sharedTexture` claim first, frame forwarding reports `desktop-shared-texture-claimed` until it or the Desktop Host's `sharedTexture` service reloads; it does not take the claim over when the other holder releases it. The Host-to-Main boundary is Desktop's own audited boundary and does not change with this package.

<a id="understand-the-implementation"></a>
## Understand the implementation

The workspace keeps the [native receiver](native/receiver.cc) and transport alongside the plugin. Desktop compiles them for its target architecture. The plugin’s npm package excludes the native sources and binary. Each channel is a stable listener; each producer connection owns its Mach ports or pipe instance, its frames and allocations, its credit, and its relay state, and the [channel note](../../../.agents/notes/implemented/architecture/2026-10-18-frame-forwarding-channels.md) owns the handoff rationale. When the producer's GPU differs from Chromium's, the Windows receiver reads each frame back and uploads it to Chromium's adapter, returning the producer's credit after the readback; a frame the producer marks replaceable (`frame_replaceable`, set by `dsh_frame_forwarding_submit_latest`) then replaces staged replaceable frames whose upload has not begun, while request frames stay queued in order.

Windows relay keeps one import per allocation across staging slots, reusing it only for the same NT object and dimensions. Allocation retirement clears cached imports before returning credit; active GPU copies retain their source until completion.

The Host [forwarder](src/host/forwarder.ts) creates receivers under one shared budget, binds each channel to at most one producer connection (closing the channel when that producer disconnects), retains an idle viewport for initial connection delivery, attaches the native sink of `sharedTexture.nativeSink` to each receiver, and keeps each receiver's presentation gate current: frames from the connected producer up to the latest viewport's version, including earlier generations, while that viewport is visible. The gate moves before each viewport is sent, so a frame that reaches the receiver before its acknowledgement reaches the Host's JavaScript still passes. The receiver presents each frame that passes the gate in native code, through that sink, with its Host-local handle and the frame metadata, so frames do not pass through the Host's JavaScript; it returns a frame outside the gate, or with invalid metadata, to its producer at once. A delivery returns to the receiver only after Desktop settles the presentation; an `invalidated` settlement stops the receiver before it releases the frame and the forwarder then closes the channel as `lost`, and a presentation failure is reported to the renderer as a `presentation` error without closing the channel. A frame that Desktop alone refuses, for example at its presentation limit, is one such failure and leaves the receiver's sink attached; a receiver whose sink lost its connection to Main detaches it and delivers its next frame to the forwarder instead, which returns it to the producer and attaches a new sink to every channel. On Windows every channel takes Chromium's compositor adapter from `sharedTexture.adapterLuid()`, the LUID Desktop Main reads from a texture the compositor exports and reads again after Chromium's GPU process restarts, so each channel follows Chromium's current adapter. The Host plugin is a Typert Remote service: `viewport` applies the renderer's viewport to a channel, and each `events(signal)` subscription replaces the previous one. It streams a snapshot of every channel's state, then states with increasing sequence numbers and frame errors with their source, to the current renderer; unread events beyond `maxQueuedEvents` become a new snapshot.

The Client half consumes the Client `sharedTexture` service (which the shared-texture Client plugin provides from Desktop's preload bridge) from its start to its disposal, also while no channel is open, routes each texture to its receive channel by the `rx` in its metadata and releases textures that carry none, sends viewports through the `viewport` Remote, and applies channel states in sequence order, with each snapshot replacing the states it knew; a channel absent from a new snapshot is reported `lost`, since the renderer cannot know why it closed. A closed channel's state stays until its consumer detaches, and only the 64 newest closed channels without a consumer keep theirs, so a late consumer still learns of the closure. Closing a receive channel detaches its frame and event callbacks before notifying close listeners, so a listener can reconnect the same `rx`. A [receive channel](src/client/rx.ts) holds only the frame being drawn and at most one newest stream frame behind it, so the Host's per-channel limit bounds the renderer without a queue of its own.

Desktop's internal shared-texture service, the Mach ingress, and the hop that carries handles into Electron Main belong to the [Desktop application](../../../apps/desktop/README.md); this package holds their only claim, and the [design record](../../../.agents/notes/implemented/architecture/2026-10-15-desktop-shared-texture-api.md) owns the ownership rationale.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

- During scroll or zoom, media playback and CSS placement can update on different frames. A submitted generation is not a display acknowledgement.
- Supported on macOS and Windows Desktop only; other Hosts report `unsupported-platform` or `desktop-shared-texture-unavailable`.
- Desktop answers a presentation once the renderer has imported the texture, so a renderer main thread blocked longer than `requestTimeoutMs` (10 s by default) reports that frame as failed, and the frame returns to its producer only when Desktop settles it; shorter stalls deliver the producer's newest frame when the renderer resumes.
- The Host does not learn of a renderer-side consumer failure; a consumer finds out when its next operation on the receive channel rejects.
- A producer that stays connected while it stops responding keeps its channel until it exits or the channel closes; nothing preempts it.
- Each connection can have at most 256 producer events pending in Host JavaScript: messages, presentation errors, and frames not handed to Desktop. Exceeding the limit disconnects that producer with a reason, and the Host forwarder closes the channel as `failed`. The receiver coalesces `rejected` warnings while one is pending.
- A GPU-process exit, renderer exit, committed navigation, or window closure invalidates the textures on screen and closes their channels as `lost`; the consumer opens a new channel to continue.
- Producers and receivers of protocol 1, such as the LibreOffice Kit 0.2.3 SDK and earlier, are refused; producers, receivers, and engines upgrade together.
- On Windows the receiver opens each producer process to duplicate its frame handles, so a producer must run as the Host's user at or below the Host's integrity level. The receiver cannot open a producer elevated above the Host and closes that connection during the handshake without a Host diagnostic.
- On Windows the receiver keeps one listening pipe instance and opens the next only after it hands a candidate the current one, so a process of the Host's user that connects with a wrong credential every few milliseconds can keep the pipe busy. A producer retries a busy pipe until its connection deadline, 10 seconds by default or the timeout passed to `dsh_frame_forwarding_connect_with_options`, and gives up early only after the pipe name has been absent for 500 ms without interruption; every busy reply restarts that count. Such a storm therefore fails a producer only if it lasts until the deadline, with `receiver unavailable`, or `connection cancelled or timed out` when the producer passed a timeout. A second listening instance would close the gap.
- On Windows, when the producer's GPU differs from Chromium's, a producer trimming an invisible view returns its source allocations but not its relay targets and staging surfaces: they keep their GPU memory and their share of `maxBytes` at the largest allocation size until the connection ends.

### Dev Note

<details>
<summary>Working context for maintainers</summary>

The [native e2e](tests/receiver-native.e2e.ts) compiles a test producer, connects separate producer processes with a copied credential, takes over after a crash once the held frame is released, refuses test producers built with another protocol version, without transferable channels, or without producer-local handles, and returns a trimmed producer's idle allocation to another channel sharing its budget. The [Desktop bridge e2e](tests/desktop-bridge-native.e2e.ts) attaches a fixture sink that implements Desktop's sink ABI: frames outside the deliverable state and frames with invalid metadata return their credit without a presentation, a presented frame carries its identity as metadata and returns its credit when the sink releases it, an invalidated settlement stops the channel before the release, a frame Desktop refuses leaves the sink attached while a sink that lost its connection is detached so later frames reach JavaScript, and settlements after the receiver closed are safe; when Desktop's addons are built, frames cross Desktop's hop sink into Desktop's ingress and follow Main's settlements. The [Kit frames e2e](tests/kit-frames-native.e2e.ts) opens a two-slide deck in the installed Kit's LibreOffice process, forwards its frames to an in-process Desktop, and reads IOSurface pixels: requested frames arrive under their identifiers and return credit on release; while Desktop holds every slideshow frame the slideshow state still advances, then one release delivers the newest slide; and a replacement engine, normally and after a crash, connects only after the previous engine's frame is released and renders at the replayed viewport; it is skipped while the installed Kit speaks another protocol version than this receiver. The native suites run with `pnpm exec vitest run --config vitest.e2e.config.ts packages/experimental/frame-forwarding` on macOS after the Desktop native build; the Desktop bridge e2e also runs on Windows.
